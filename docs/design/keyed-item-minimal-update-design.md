# keyed list item 内部更新の最小差分化設計（イシュー #1379）

## 1. 目的とトレーサビリティ

- 本書はベンチ起点トラッキング #1371（CSR 性能・wasm payload 改善）の
  区間プロファイル実測を起点に、`KeyedOp::Update` 適用時の子ノード列
  **全再構築**を「浅い最小差分」へ置き換える設計を確定する Phase 2 の
  承認ゲートである。**本書は設計のみを成果物とし、コード変更を含まない**。
  後続実装は #1381（最小差分化本体の実装）・#1382（`sync_attrs` 属性値の
  同値スキップ）が担う。本 PR のマージ（ユーザー承認）をもって #1381・
  #1382 の着手条件とする。
- 解決する課題: `crates/wasm-client/src/keyed_apply.rs` の `KeyedOp::Update`
  適用（1349 行目以降）は、子ノード列が新旧で一致しない場合
  `replace_item_children`（detached 構築 → `exchange_children` による
  全交換）へ進む。これは 1 文字のテキスト変更であっても子ノード列全体を
  作り直し全交換するため、Text ノード 1 個への `set_data`（`CharacterData.data`
  代入）1 回で足りるはずの更新が、要素生成・属性設定・`insertBefore`/
  `removeChild` の web-sys 境界呼び出し列へ膨張する。親 #1371 の区間
  プロファイル実測では update 操作の wasm 内時間の大半が DOM 適用
  （web-sys 境界呼び出し）に費やされており、この全再構築が主要因の一つ
  と判明している。
- 参照フレームワークの知見: lit（`_commitText` = 既存 Text ノードへの
  `node.data` 代入 + 同値スキップ）・preact（`dom.data` 直接代入）・vue
  （patchFlag によるテキストのみ更新の特化経路）はいずれもテキスト更新を
  既存ノードへの最小書き込みで済ませている。本書はこの知見を keyed list
  Update op の適用層（wasm-client）へ、`docs/policy/intentional-non-adoption.md`
  §3.1（仮想 DOM非採用）の評価軸を破らない形で取り込む方式を確定する。
- 既存設計との関係: `docs/design/keyed-update-op-design.md`（以下「Update
  op 設計書」、イシュー #1322/#1323/#1324）§3.2 が確定した適用意味論
  （c 案「浅い in-place 更新（深さ 1 打ち切り）」、d 案「ノード全体の
  再帰 diff」の却下）を前提とする。本書は c 案のうち**「子孫のさらに
  内側だけを選択的に更新する再帰比較は行わない」という深さ 1 打ち切り**
  を正式に撤回・改訂し、「新旧ノードの種別・タグが値比較で同型と確認
  できる限り、子孫のさらに内側へも同じ規則を再帰適用する」意味論へ
  置き換える（改訂理由・d 案却下根拠との非該当は §4 で論証する）。
  一方、c 案が確定するそれ以外の意味論（アイテムルート要素の同一性維持・
  タグ不一致時のアイテム全置換・不一致時 fail-closed）のうち、タグ
  不一致時のアイテム全置換・不一致時 fail-closed は変更しない。**アイテム
  ルート要素の同一性維持については、本書 §6 が確定する 3 段エスカレー
  ションの導入に伴い、無条件の維持から「段 1 の最小差分書き込みで
  Update が完結するハッピーパス（タグが一致し、かつ段 1 の書き込みが
  すべて成功する経路。実運用の支配的ケース）に限る」条件付きの維持へ
  縮小する**（本改訂で明記、PR #1395 codex-review 継続指摘 P0 対応。
  当初「深さ 1 打ち切りのみを撤回し、それ以外は変更しない」としていた
  のは誤りであり、段 2 の導入自体がルート同一性契約の適用範囲を狭める
  という副作用を見落としていた）。段 1 の書き込み単位が実行時に失敗した
  場合（§6.2 段 1 (B)、ポリシー拒否は含まない）、または段 1 (A) の
  narrow fallback（`replace_item_children`。子数・種別・タグの通常の
  構造変更に対しても試みられるが、そのこと自体では段 2 まで進まない）が
  実行時に失敗した場合（本改訂で追記、PR #1395 codex-review 9 巡目 P1
  対応。以前の版は §6.2 段 1 (B) のみを挙げており、段 1 (A) の narrow
  fallback 自体の実行時失敗という別の発火条件を見落としていた）は、
  タグが一致していても段 2（`create_item`+`replace_root` によるアイテム
  ルート要素の差し替え）へ進むため、ルート要素の DOM ノード参照・外部
  保持の要素参照・フォーカス・選択状態は失敗経路では保持されない。
  詳細・影響範囲は §6.2 参照。Update op 設計書 §3.2 の当該箇所には、
  本書への改訂を示す追補（撤回範囲を明示）を追記する（§9 参照）。

## 2. 現状整理（設計の前提事実）

- `crates/core/src/keyed.rs::diff_keyed_items`（core 側、#1323）は保持
  キーの新旧 `Node` を `PartialEq`（部分木全体の構造的同値比較）で比較し、
  不一致のときのみ `KeyedOp::Update { key }` を発行する。**アイテム単位の
  二値判定**であり、差分位置の再帰的特定は行わない（Update op 設計書
  §3.1）。この core 側の契約は本書では変更しない。
- `crates/wasm-client/src/keyed_apply.rs::apply_ops_with_items` の
  `KeyedOp::Update` arm（1349〜1533 行）は次の順で適用する:
  1. `find_by_key` でハンドル解決（O(n²) 退行防止のハンドルキャッシュ
     経由、`Remove`/`Move` と共通）。
  2. ライブ DOM への `tag_name` 照会でルート要素タグの一致判定。不一致
     なら `create_item` + `replace_root` によるアイテム全置換（§3.2 却下案
     a と同じ手段だが、対象はタグ変更が実際に起きたこの 1 アイテムのみ）。
     `replace_root`（`crates/wasm-client/src/keyed_apply.rs::replace_root_node`）
     は `insert_before`（新要素を旧要素の直前へ挿入）→ `remove`（旧要素を
     除去）という 2 回の独立した web-sys 境界呼び出しからなり、挿入が
     失敗すれば旧要素に一切触れず `false` を返し、除去が失敗すれば挿入
     済みの新要素を取り除いて挿入前の状態へ**この呼び出し 1 回の内部で**
     ロールバックしてから `false` を返す（ロールバック自体が失敗する
     残余リスクは `on_rollback_failed` 経由で警告するのみで、Update op
     設計書 §6 不変条件 6 が既に認める「副作用は完全な原子性を主張しない」
     の既存の限定である）。**この呼び出し内ロールバック契約は
     `replace_root_node` という単一呼び出しの内部にのみ及び、Update op
     適用全体を巻き戻す手段ではない**（本書 §6 で改めて注意する）。
  3. タグ一致の場合、`replace_item_children`（子ノード列を detached
     コンテナへ `build_dom_node` でプログラム的構築 → 構築成功後
     `exchange_children` で `remove_child`×旧子数 + `insert_before`×新子数
     の全交換、部分失敗時はロールバック）を**先に**試みる。成功した
     場合にのみ `sync_attrs` を呼ぶ（順序反転は PR #1340 の codex-review
     指摘対応で確定済み。属性同期を先に行うと `replace_item_children`
     失敗時に「属性は新・子ノードは旧」の不整合状態が残るため）。
  4. `replace_item_children` が失敗（`RawHtml` 混入・要素生成失敗等）した
     キーは（現行コードでは）`stale_update_keys` へ記録し、ライブ DOM は
     旧内容のまま据え置く（fail-closed。この手順の適用範囲は「アイテム
     ルート直下の子ノード列全体」のみであり、それより内側の選択的な
     更新は行わないため、旧のままか新のままかの二値で足りる）。**この
     二値性は、`replace_item_children` という単一の detached 構築 +
     全交換オペレーションが「構築を先に完了させてからのみライブ DOM を
     書き換える」という、その呼び出し 1 回に閉じた原子性を持つことに
     由来する**（Update op 適用全体の原子性ではない点に注意。詳細は
     §6）。
  子ノード列は 1 文字のテキスト変更であっても全子ノードを detached
  構築 → 全交換しており、本書が最小差分化の対象とするのはこの手順
  （上記 3.）である。手順 1・2 の枠組み（ハンドル解決・タグ不一致時の
  アイテム全置換）は変更しない。一方、手順 4 の終端（`stale_update_keys`
  を Update op 適用の事実上の唯一の失敗時終端として扱う設計）は、本書
  §6 で確定する 3 段エスカレーション設計により変わる: 本書が導入する
  per-child diff は、1 回の Update op 適用の中で `set_data` /
  `sync_attrs` / narrow な `replace_item_children` を複数回・独立に
  呼び出す構成であり、これらのいずれかが失敗する組み合わせは手順 4 が
  前提としていた「1 回の detached 構築 + 全交換のみが失敗しうる」という
  単純な状況を超える。本書はこの局面に対し、**「旧のままか新のままかの
  二値を保証する」という目標自体を撤回**し、代わりに「いかなる失敗経路
  でも常により広い範囲の新規構築へ前進し、最終的に確立済みの
  `resync_required` 契約（PR #1391/#1392 で確定済み、ライブ DOM を直接
  読み出す構造フォールバックへ委譲する。呼び出し元がこの委譲をいつ
  消費するかの契約は本書 §6.1・§6.2 が確定する）へ合流する」という
  異なる性質の契約を定義する（詳細は §6）。undo ログのような
  新しいブックキーピングは一切追加しない（PR #1395 codex-review 指摘
  4 件対応で undo ログ方式は撤回済み。さらに後続の再帰的スコープ
  エスカレーション方式も P0 指摘 2 件を受けて本改訂で撤回する。§6 参照）。
- 「達成 Node」キャッシュ契約（#1330/#1340、モジュール冒頭 doc「cache-miss
  フォールバックの達成契約」）: `apply_ops_with_items` は次回比較用の
  旧 `Node`（`old_items` 相当）を、in-place 更新の成否に応じて合成する
  （`compose_achieved_children`）。**cache-miss フォールバック経路
  （`stale_update_keys` 由来ではなく、保持キーに対応する直前の `Node` が
  何らかの理由でキャッシュに存在しなかった場合）ではプレースホルダの旧
  `Node` が渡され、内容比較を強制的に不一致にする**（ルート要素タグ
  一致判定をキャッシュではなくライブ DOM 照会にしている理由と同じ:
  プレースホルダの内容は per-child 差分の根拠に使えない）。
- `keyed_apply.rs` は「純粋層（native テスト可能、`ChildExchangeDom` /
  `RootReplaceDom` トレイト抽象でモック注入する）+ wasm32 配線層
  （`crates/wasm-client/src/keyed_dom.rs::WebSysKeyedDom`）」の 2 層構成
  であり、部分失敗時のロールバック（構造的原子性）をモックテストで
  検証する既存方式を継承する。
- Update op 設計書 §3.2 は d 案「ノード全体の再帰 diff（morphdom 型）」を
  §5（`intentional-non-adoption.md` §3.1 と同じ評価軸）に基づき既に却下
  済みであり、§5 の 4 軸論証（明示性・決定性・機械検証可能性・コンテキスト
  消費）を本書の論証テンプレートとして踏襲する。
- `docs/policy/intentional-non-adoption.md` §3.1 には stale な記述がある
  ことが判明しているが、その是正は**並行イシュー #1380 の担当**であり、
  本書・本イシューでは同ファイルを編集しない（コンフリクト回避・
  スコープ分離）。
- Phase 3 の #1384「アイテムの構造同型判定と束縛点パス導出（core 側）」が
  下記 §3.2 の (b) 方式と技術的に隣接する。

## 3. 方式選定

### 3.1 比較する 2 方式

| 方式 | 内容 | 判定 |
|------|------|------|
| (a) 位置対応の浅い子ノード diff | 達成 Node キャッシュの旧子ノード列と新子ノード列を**位置対応（インデックス同順）**で比較し、Text↔Text は `set_data` 1 回、Element↔同タグ Element は属性差分 + 子への同規則を**同じ深さで再帰適用**、前提が崩れたら崩れた**部分木のみ**（アイテムルート直下での不一致はアイテム全体）を従来の detached 構築 + `exchange_children` へフォールバックする | **採用**（§3.2 で詳細確定） |
| (b) 束縛点限定更新（`data-bind-text` の keyed list 内への一般化） | アイテム内部の束縛点を明示宣言し、その束縛点のみを直接更新する API 面の拡張 | **不採用**（比較記録として残す。§3.3） |
| 併用（(a) を既定とし (b) を明示宣言時のみ優先） | (a)・(b) 双方の適用面を持つ | **不採用**（(b) 自体を見送るため単独では成立しない） |

判定根拠: 親 #1371 の区間プロファイル実測（wasm 内時間の 92〜98% が
DOM 適用、Node 木構築コストは 1,000 行スケールで 0.09ms と軽微）より、
Rust 側の比較コストは安価であり、削減すべきは web-sys 境界呼び出し回数
そのものである。(a) はこの実測と直接整合し、lit/preact/vue の参照実装
知見（テキスト更新は既存ノードへの最小書き込み）とも一致する。

### 3.2 (a) 位置対応の浅い子ノード diff の適用規則

達成 Node キャッシュの**旧**子ノード列（`compose_achieved_children` が
維持する `Node`）と、diff 対象の**新**子ノード列（`new_children`、
`Node::Element { children, .. }`）を先頭から同一インデックスで突き合わせる。

フォールバック粒度は 2 種類の事象に応じて決まる。判定・エスカレーション
先の詳細な契約（**段 1 の narrow local fallback → 段 2 の item 全置換 →
段 3 の `resync_required`** というフラットな 3 段ラダー）は §6 で確定
する。本節では per-child 規則そのもの（どの条件でどちらの事象に分類
されるか）と、事象発生時に**まずどのスコープへ narrow fallback を試みる
か**のみを定義する。

フォールバックを発火させる事象は 2 種（本改訂で (B) を追加、PR #1395
codex-review 指摘 4 件対応。詳細・区別の理由は §6 参照）:

- **(A) 前提不一致**（書き込み前、Rust 側の値比較・ライブ構造観測の
  値比較のみで判定し、web-sys 境界への書き込みは一切発生しない）:
  子数不一致・種別不一致・タグ不一致（達成 Node キャッシュ由来、以下の
  規則）、または §3.2a が定義するライブ子ノード列の構造観測がキャッシュ
  前提と一致しない場合（§3.2a 参照）。このスコープの書き込みは 1 件も
  始まっていないため、まずこのスコープ自身（比較対象の子ノード列を
  持つ要素そのもの。アイテムルートなら既存 `replace_item_children` の
  対象、それより内側なら §3.2a の `as_element` で得たハンドルを同じ
  `replace_item_children` へ渡した対象）へ**narrow**（そのスコープの
  子ノード列のみを対象とし、要素自身の識別子・属性には一切触れない）な
  detached 構築 + 交換フォールバックを試みる。この narrow fallback が
  **成功**すれば、このスコープを含むアイテム内の他のスコープの適用は
  影響を受けず継続する。narrow fallback**自体が失敗した場合**は、この
  スコープに閉じた再試行や一つ外側のスコープへの段階的な波及は行わず、
  アイテム全体について残る段 1 処理をすべて打ち切り、直ちに§6 の段 2
  （item 丸ごと差し替え）へ進む。
- **(B) 書き込み失敗**（実際に web-sys 境界への書き込みを試みた後に
  判明。新規、§6 参照）: Text の `set_text_data` が `false` を返す場合、
  または Element の `sync_attrs` の戻り値が**「ポリシー拒否を除いた
  期待 achieved 集合」**と一致しない場合。**「ポリシー拒否を除いた期待
  achieved 集合」とは、`new_attrs` のうち
  `is_attr_write_rejected`（`crates/wasm-client/src/keyed_apply.rs`、
  イベントハンドラ属性・危険 URL スキーム・不正 `srcset` の判定述語、
  `crate::keyed_dom::WebSysKeyedDom::sync_attrs` が web-sys 実装として
  共有する同一述語）が `false` を返すエントリのみを取り出した部分集合
  を指す**（本改訂で判定基準を精緻化、PR #1395 codex-review 継続指摘
  P0 対応）。判定は次の 2 条件のいずれかが破れた場合に (B) とする:
  (i) この部分集合の各 `(name, value)` について、`sync_attrs` の戻り値
  に `(name, value)` と完全一致するエントリが存在すること。(ii) 戻り値
  に `new_attrs` に存在しない名前のエントリ（`removeAttribute` の実行時
  失敗により削除できず残存した属性）が 1 件も含まれないこと。
  `is_attr_write_rejected` が `true` のエントリ（ポリシー拒否）は
  この判定に**一切用いない**: ポリシー拒否は `docs/design/keyed-update-op-design.md`
  §3.2 c 案・本書「属性検証規則の共有」が定める**意図的な skip**であり、
  `crates/wasm-client/tests/`／`crates/wasm-client/src/keyed_apply.rs`
  の既存テスト（`compose_achieved_children_keeps_old_value_when_attr_update_is_rejected`・
  `compose_achieved_children_omits_attr_when_new_attr_addition_is_rejected`）
  が固定するとおり、拒否時は実 DOM の旧安全値（存在すれば）またはその
  属性の不在をそのまま「達成」として扱い、失敗として扱わない契約が
  既に確立している。本書の (B) 判定がこの契約を上書きしないよう、
  ポリシー拒否と実行時失敗（`setAttribute`/`removeAttribute` の `Err`）
  を明確に分離する。**このユニット（Text ノード・Element ノード）自身
  への narrow fallback は（(B) と判定された場合に限り）一切試みない**
  （Element 自身の属性書き込み失敗は、その Element を子として含む親
  スコープの子ノード列交換でしか本質的に修復できず、その Element 自身
  の子ノード列交換〔narrow fallback〕では属性に触れられないため。
  本改訂で明確化、P0-1 対応）。(B) と判定された時点で、アイテム全体に
  ついて残る段 1 処理をすべて直ちに打ち切り、§6 の段 2（item 丸ごと
  差し替え）へ進む。ポリシー拒否のみで (B) に該当しない場合は、段 1 の
  この単位は成功として扱い、`sync_attrs` の戻り値（ポリシー拒否分の
  旧値・不在を含む、実 DOM の実際の状態）をそのままこのスコープの達成
  内容として用いる（§5 参照）。

1. **子数が一致し、かつ各インデックス `i` の新旧ノードが同種
   （Text↔Text または Element↔Element かつ同タグ）である場合のみ**、
   以下の per-child 規則を適用する。子数不一致・種別不一致・タグ不一致が
   1 箇所でもあれば、上記 (A) に従いこのスコープへ narrow fallback する
   （前提判定は Rust 側の値比較のみで行い、フォールバック判定自体が
   web-sys 境界を呼ぶことはない）。
2. **Text ↔ Text**: `PartialEq` で旧新の文字列値が同値ならスキップ
   （境界呼び出しゼロ）。不一致なら該当 Text ノードへ `set_data` を 1 回
   呼ぶ（`innerHTML`/`insertAdjacentHTML` は経由しない。§4 のセキュリティ
   不変条件参照）。失敗（(B)）した場合は上記のとおりアイテム全体が
   段 2 へ進む。
3. **Element ↔ 同タグ Element**: 属性集合の差分適用（Update op 設計書
   §3.2 c 案が定義する `sync_attrs` の検証規則をそのまま再利用する。
   規則を複製しない）を行う。**`reserved_attr` 引数（`sync_attrs` の
   予約属性名パラメータ、§2 参照）は、対象がアイテムルートか子孫かで
   異なる**（本改訂で明記、P1-3 対応）: アイテムルートは既存の正規化
   契約どおり `data-key` を渡し、`new_attrs`/`old_attrs` から `data-key`
   を除外したうえで呼び出し、達成 Node 合成時に `new_node` 側の
   `data-key` の値をそのまま再付加する（既存の
   `compose_in_place_updated_node` 契約、変更なし）。**子孫（非ルート）
   の Element は既定では `data-key` のような予約属性を持たないため、
   `reserved_attr` には「一致する属性名が存在しない値」（空文字列相当）
   を渡し、`new_attrs`/`old_attrs` は一切フィルタしない。ただし、その
   子孫がネストした binding のルート（`data-bind-list`
   〔`fandhe_frontend_core::keyed::BIND_LIST_ATTR`〕を持つ Element、
   §6.3 が扱うネスト keyed list のルート）である場合は例外とする。**この
   例外は、旧新の `data-bind-list` 値が一致する場合に限る**（本改訂で
   条件を精緻化、PR #1395 codex-review 11 巡目 Bugbot Medium 対応。
   以前の版は値の一致を問わず常に予約扱いとしていたが、これは誤りで
   あり撤回する）:
   - **旧新の `data-bind-list` 値が一致する場合**（達成 Node キャッシュ
     側 `old_attrs` の `data-bind-list` 値と `new_node` 側 `new_attrs`
     の `data-bind-list` 値が文字列として同一。両方に存在することが
     前提で、この場合は同一の binding field を指し続けていることを
     意味する）: `data-key` のアイテムルート扱いと同型に `reserved_attr`
     へ `data-bind-list` を渡し、`new_attrs`/`old_attrs` から
     `data-bind-list` を除外したうえで `sync_attrs` を呼び出す。達成
     Node 合成時に再付加する値は、**旧新一致が確認済みのこの値**（すなわち
     `old_attrs`／`new_attrs` いずれの表記でも同一の値）を使う（本改訂で
     明記: 「`new_node` の値をそのまま再付加する」という以前の記述は、
     この値が旧値と一致することを何ら検証せずに信頼する体裁になって
     いたため撤回する。旧新一致を確認したうえで初めてこの値を「ライブ
     DOM が実際に保持し続ける値」として扱える。`sync_attrs` はこの
     属性を一切書き込まないため、ライブ DOM の実際の値を個別に読み
     戻す新しい API は不要であり、旧新一致の確認自体が「ライブ DOM が
     この値を保持している」ことの根拠になる）。
   - **旧新の `data-bind-list` 値が異なる場合（追加・削除・値変更の
     いずれか）**: これは binding identity の構造変更（このスコープが
     指すネスト keyed list の field 名そのものが変わった、または
     binding ルートであること自体が変わった）であり、単なる属性値の
     更新として扱わない。**(A) 前提不一致として扱い、このスコープへ
     narrow fallback する**（本改訂で追加。`reserved_attr` による保護
     対象にはしない。理由: `data-bind-list` を通常の属性として
     `sync_attrs` の比較・書き換え対象に含めてしまうと、(a) binding の
     field 識別子そのものが Update 経路から書き換わる、(b) `sync_attrs`
     は既存 DOM ノードを再生成しないため §6.3 規則 1〜3 が定めるノード
     再生成トリガーに一致せず `invalidated_nested_fields` へのキャッシュ
     無効化も走らない、という 2 点で §6.3 のネスト binding キャッシュ
     契約が壊れる。narrow fallback〔`replace_item_children`〕はこの
     スコープの子ノード列を detached 構築 + 交換するため、新しい
     binding ルート要素〔新しい `data-bind-list` 値を持つ〕が正しく
     生成され、§6.3 の通常の無効化契約がそのまま働く）。**このスコープの
     narrow fallback が成功した場合、無効化すべき nested field は新しい
     `data-bind-list` 値だけでなく、旧い `data-bind-list` 値も含む**
     （詳細・理由は §6.3 参照。narrow fallback 後の新しい部分木を
     `collect_nested_bind_list_fields` で走査しても旧い field 名は
     現れないため、この位置での値相違を検出した時点で旧い field 名を
     別途記録しておく必要がある）。既存の `sync_parent_attrs`
     〔`crates/wasm-client/src/keyed_apply.rs`〕が親要素の `data-bind-list`
     を同じ理由で予約属性として扱う既存パターンは、旧新一致ケースの
     処理としてそのまま踏襲する。この例外を除き、通常の（binding
     ルートでない）子孫の成功判定（上記 (B) の基準）は未フィルタの
     `new_attrs` を基準に行い、達成 Node 合成でも `sync_attrs` の戻り値
     をそのまま使う（再付加の後処理は不要）。失敗（(B)）した場合は
     上記のとおりアイテム全体が
   段 2 へ進む（この Element 自身の子ノード列交換は試みない。
   P0-1 対応）。属性適用が成功した場合、その要素の子ノード列へ本節の
   規則を**同じ深さで再適用**する（新旧の種別・タグが同型と確認できる
   限り、子孫のさらに内側へも同規則を適用し続ける。子孫の内側だけを
   選択的に更新するこの再帰は Update op 設計書 §3.2 c 案の当初「深さ 1
   打ち切り」定義が明示的に除外していたものであり、本書 §1・§4 で正式に
   撤回・改訂したうえで採用する）。子孫レベルで (A) 前提不一致に遭遇
   した場合は上記 (A) に従い、その部分木（＝現在比較中の Element 1 件）
   へ narrow fallback する（成功すればそれより上位・兄弟の適用は継続、
   失敗すればアイテム全体が段 2 へ進む。中間スコープを経由した段階的な
   エスカレーションは行わない）。子孫レベルで (B) 書き込み失敗に遭遇
   した場合も同様にアイテム全体が段 2 へ進む。
   `RawHtml` ノードへ子孫が到達する場合は、Update op 設計書 §3.2 と同じく
   `build_dom_node` の既存契約（`None` を返す）に従い、その部分木への
   narrow fallback を試み、この構築自体が失敗すればアイテム全体が段 2
   へ進む（新規の HTML 解釈経路を作らない）。
4. **打ち切り（撤回済み）の意味の引き継ぎ方**: Update op 設計書 §3.2
   c 案が当初定義した「深さ 1 打ち切り」（ルート属性比較 1 回 + 子ノード
   列同値判定 1 回のみで、子孫のさらに内側は変更があれば丸ごと再構築し
   選択的な再帰比較は行わない）は、本書が正式に撤回する（§1・§4 参照）。
   撤回するのは**再帰する深さ**のみであり、c 案が定義する他の意味論
   （ルート要素の DOM ノード同一性はハッピーパスでは保持するが、内容が
   変わった部分木の DOM ノード同一性・内部フォーカスまでは保持しない
   契約、§3.3 参照）は変えない。**ただし、ルート要素の DOM ノード同一性
   自体は本書が新たに導入する段 2（§6.2）によって、段 1 のいずれかの
   単位が実行時に失敗した場合には保持されなくなる。これは「深さ 1
   打ち切りの撤回」とは独立した、段 2 の導入という**別の変更点**に
   起因する契約の縮小であり、§1・§6.2 で正直に明記する**（本改訂で追加、
   P0 対応）。同型が続く限り再帰的に最小差分化する点が撤回前の c 案
   「子ノード列は不一致なら全再構築」との違いであり、「探索」（どの子と
   どの子を対応付けるか推定する処理）は一切行わない（位置対応のみ、
   §3.4 参照。この非探索性・決定性が d 案却下根拠との非該当を成立させる
   軸であり、再帰する深さそのものとは独立である。§4 参照）。

### 3.2a 子ノードハンドル抽象（新設トレイト、codex-review 指摘対応）

§3.2 の per-child diff は、アイテムルート要素だけでなく**子孫のさらに
内側**の Text ノード・Element ノードへ直接書き込む（`set_data`・
`sync_attrs`・部分木 `replace_item_children`）。既存
[`KeyedListDom`]（`crates/wasm-client/src/keyed_apply.rs`）はキー付き
アイテムの**ルート要素**を `find_by_key` で解決した後に呼ぶ API 群
（`sync_attrs`/`replace_item_children`/`tag_name` はいずれも `&Self::Handle`
を取り、web-sys 実装ではこれは `web_sys::Element` そのものでありアイテム
ルートに構造的に限定されない汎用の Element ハンドルである）であり、子孫の
Text ノード・任意深さの Element ノードへ実際に**到達するための走査手段
そのもの**は持たない。**本書は「既存シグネチャの流用のみで済む」という
当初記述（旧稿）を撤回し、新しい小さなトレイトを 1 個新設することを
正式な設計として確定する**（PR #1395 codex-review 指摘スレッド 1 対応）。

- **新設トレイト `ChildNodeDom`**（`keyed_apply.rs` の純粋層に追加する
  別トレイト。既存 `KeyedListDom` のメソッド・シグネチャは 1 つも
  変更しない）:
  - `type ChildHandle: Clone;` — DOM 上の子ノード 1 個（Text または
    Element のいずれか）を指す新しいハンドル型。web-sys 実装では
    `web_sys::Node`（`Element`/`Text` の共通スーパータイプ）を想定する。
  - `fn child_handles(&mut self, parent: &Self::Handle) -> Vec<Self::ChildHandle>;`
    — `parent`（既存 `KeyedListDom::Handle`。アイテムルートでも、per-child
    diff で降りた任意深さの Element でも同じ型を再利用する）直下の子
    ノードを DOM 順で列挙する（`Node::childNodes` 相当）。この列挙結果への
    **位置（インデックス）アクセスのみ**を per-child diff が使う（§3.2 の
    「位置対応のみ、探索は行わない」不変条件をハンドル取得層でも保つ。
    列挙自体はアイテム 1 件・部分木 1 件あたり高々 1 回の走査であり、
    §3.2 が既に許容している「Rust 側の値比較コストは安価」という前提の
    範囲内に収まる）。
  - `fn child_kind(&mut self, node: &Self::ChildHandle) -> ChildNodeKind;`
    （`enum ChildNodeKind { Text, Element, Other }`。**`Other` は本改訂で
    追加、PR #1395 codex-review 11 巡目 P1-2 対応**）— 種別判定
    （`Node::nodeType` 相当）。`Other` は hydrate 後に残存するコメント
    ノード（`<!-- -->`）・外部コード挿入の CDATA・processing instruction
    等、達成 Node キャッシュが表現できる `Node::Text`/`Node::Element` の
    いずれにも該当しない DOM ノード種別を指す。**`child_kind` はこれらを
    `Text`/`Element` へ誤って分類してはならず、また `unreachable!()`/
    `panic!()` を用いてもならない**（fail-closed 回復経路の迂回・
    パニックによるクラッシュのいずれも避ける。旧稿は 2 値のみでこの
    ケースを表現できず、実装が誤分類かパニックのいずれかを選ばざるを
    得ない欠陥があった）。`Other` を返した位置は、下記「ライブ観測と
    キャッシュ前提の整合チェック」規則 2 の種別一致判定において
    `Node::Text`/`Node::Element` のいずれとも一致しないため、この位置を
    含むスコープは自動的に (A) 前提不一致として narrow fallback へ
    倒れる（新しい判定ルールを追加する必要はなく、既存の種別不一致
    判定がそのまま `Other` を吸収する）。
  - `fn as_element(&mut self, node: &Self::ChildHandle) -> Option<Self::Handle>;`
    — `child_kind` が `Element` の場合のみ `Some` を返し、既存
    `KeyedListDom::Handle`（`sync_attrs`/`replace_item_children`/
    `tag_name`/`child_handles` 自身への再入力）として使えるハンドルへ
    変換する。これにより「Element ↔ 同タグ Element」の子孫再帰
    （§3.2 規則 3）は、既存の `sync_attrs`/`replace_item_children` を
    アイテムルート以外の任意深さの Element へもそのまま適用できる
    （両メソッドのシグネチャ自体が元々アイテムルートに限定していない
    という事実は変わらないため、この 2 メソッドへの変更は不要）。
  - `fn set_text_data(&mut self, node: &Self::ChildHandle, value: &str) -> bool;`
    — `child_kind` が `Text` の場合の `set_data`（`CharacterData.data`
    代入）本体。DOM 標準上この代入自体は失敗しないが、実装異常系に
    備え戻り値を持たせ、既存の「戻り値で成否を報告する」他メソッド群と
    様式を揃える。この戻り値が `false` の場合は §3.2 (B)「書き込み失敗」
    に該当し、§6 の段 2 へ進む。
  - `fn text_data(&mut self, node: &Self::ChildHandle) -> String;`
    （新設、本改訂で追加、PR #1395 codex-review 指摘スレッド 2 対応）
    — `child_kind` が `Text` の場合の `CharacterData.data` の**読み取り**
    専用参照。書き込み（`set_text_data`）とは別メソッドとし、下記
    §3.2a の「ライブ観測とキャッシュ前提の整合チェック」からのみ呼ばれる
    （per-child 規則そのものは新旧値の `PartialEq` のみで決まるという
    §3.2 規則 2・§4「決定性」の不変条件は変えない。ライブ値の読み取りは
    前提が成立しているかの検証にのみ用い、適用計画の分岐条件には使わない）。

**ライブ観測とキャッシュ前提の整合チェック（前提不一致 (A) の一種、
本改訂で新設、PR #1395 codex-review 指摘スレッド 4 対応）**: §3.2 規則 1
の前提判定は達成 Node キャッシュ（Rust 側の値のみ）で行うが、per-child
書き込みを実際に開始する**直前**に、対象スコープについて次の 3 点を
`ChildNodeDom` の観測で検証しなければならない。1 点でも成立しなければ
per-child 書き込みを 1 件も開始せず、§3.2 の統一規則により**このスコープ
自体を** (A) 前提不一致としてフォールバックする（キャッシュ由来の前提が
崩れているのと同じ扱いであり、フォールバック粒度の規則を新設しない）:

1. `child_handles(parent)` の要素数が、達成 Node キャッシュ側の旧子ノード
   列の要素数と一致すること。
2. 各インデックス `i` について `child_kind(child_handles(parent)[i])` が、
   達成 Node キャッシュの `i` 番目のノード種別（`Node::Text`/
   `Node::Element`）と一致すること。
3. 種別が `Element` のインデックスでは `as_element` が `Some` を返す
   こと（`None` はキャッシュ前提とライブ DOM の乖離を意味する）。
4. **（本改訂で追加、PR #1395 codex-review 指摘スレッド 1 対応）** 種別が
   `Element` のインデックスでは、`as_element` が返したハンドルへ既存
   `KeyedListDom::tag_name`（§3.2a 冒頭で述べたとおりアイテムルート
   限定ではない既存 API をそのまま再利用し、新規メソッドは追加しない）
   を呼び、得られたライブタグ名が達成 Node キャッシュの `i` 番目の
   `Node::Element` のタグ名と一致すること。子数・種別・`as_element` の
   成否のみでは「キャッシュ上は `<span>` だがライブ DOM 上は `<button>`
   に置き換わっている」というタグ不一致を検出できず、§3.2 規則 3 の
   「同タグ Element」前提が崩れたまま `sync_attrs`／子孫再帰へ進んで
   しまう（fail-closed 契約の迂回）。この 4 点目はその迂回を塞ぐ。
5. **（本改訂で追加、PR #1395 codex-review 指摘スレッド 2 対応）** 種別が
   `Text` のインデックスでは、新設 `ChildNodeDom::text_data` で得た
   ライブ文字列値が、達成 Node キャッシュの `i` 番目の `Node::Text` の
   値と一致すること。§3.2 規則 2 の Text↔Text 同値スキップは達成 Node
   キャッシュ上の旧新値比較（`PartialEq`）のみで判定するため、hydrate
   時の初期値ドリフト・外部コードによる直接の Text 値書き換え等で
   ライブ値がキャッシュの旧値と乖離しているにもかかわらず新値が
   キャッシュの旧値と同値であるケースでは、スキップ判定がライブ DOM を
   キャッシュどおりの誤った値のまま放置してしまう（旧来の全子ノード
   交換であれば `set_data` 相当の書き込みが必ず発生していたため収束して
   いた退行）。この 5 点目により、ライブ値がキャッシュ前提と乖離した
   Text ノードを含むスコープは per-child diff の対象から外れ、§3.2 の
   統一規則に従ってフォールバックし、新しい `Node` から改めて構築
   することで値が収束する。

この検証は**選択ではなく関門**である: ライブ観測はどの書き込み手段を
使うかを決めるためではなく、キャッシュ前提がライブ DOM 上でも成立して
いることを書き込み前に確認するためだけに使う（§4「決定性」の「比較は
位置対応 + `PartialEq` のみ」不変条件は、この関門を通過した後の
per-child 規則そのものには一切変更がないため保たれる）。SSR hydrate
由来の属性ドリフトはキャッシュとライブの**値**の乖離であり
`sync_attrs` の既存契約が吸収するのに対し、本チェックはキャッシュと
ライブの**構造**（子数・種別・Element への変換可否・タグ名・Text 値）の
乖離を検出するものであり、性質が異なるため区別する（上記 4・5 の追加に
伴い、この区別軸に「タグ名」「Text 値」も加わったことを本改訂で明記する。
タグ名・Text 値は §3.2 規則 1・2 が前提とする「同種であること」の判定
根拠そのものであり、`sync_attrs` が吸収する属性値ドリフトとは異なり
前提不一致 (A) 側で扱う）。
**書き込み単位ごとの再検証（stale ハンドル対策、本改訂で新設、PR #1395
codex-review 11 巡目 P1-1 対応）**: 上記の関門は「対象スコープについて
書き込みを開始する**直前に 1 回**」検証する設計だったが、これだけでは
不十分である。同一スコープ内で複数の書き込み単位（Text の
`set_text_data`・Element の `sync_attrs`）を**順に**適用する構成である
以上、先行する単位の書き込みが後続の単位に影響を及ぼしうる: `sync_attrs`
が内部で呼ぶ `setAttribute`/`removeAttribute` は、対象がカスタム要素
（`customElements.define` 登録済み要素）であれば `attributeChangedCallback`
を**同期的に**発火させる（CEReactions の反応キューは当該呼び出しの
末尾で同期的に処理される）。このコールバックは任意のアプリケーション・
ライブラリコードであり、後続の兄弟ノードを削除・置換する副作用を持ち
うる。この場合、スコープ開始時に 1 回だけ取得した `child_handles(parent)`
の後続位置のハンドルは detached（親から切り離された）またはライブ DOM
上の実際の内容と乖離した stale なハンドルのまま処理が継続してしまう。
stale ハンドルへの `set_text_data`/`sync_attrs` が（DOM 標準上・実装上
`false` を返さず）成功を報告すると、ライブ DOM は実際には更新されて
いないにもかかわらず達成 Node キャッシュだけが新状態として確定し、
§6.1 が保証する収束契約（達成 Node は「呼び出し後に実 DOM が実際に
表している内容」と一致する）を破る。

修正: **各書き込み単位（Text の `set_text_data`・Element の
`sync_attrs`）の直前に、そのつどそのスコープの子数・対象位置の種別・
タグ（`Element` の場合）・Text 値（`Text` の場合）を上記「ライブ観測と
キャッシュ前提の整合チェック」規則 1〜5 と同一の基準で再検証する**
（`child_handles(parent)` を毎回改めて呼び直し、スコープ開始時に取得
した古いスナップショットを使い回さない）。1 点でも乖離が検出された
時点で、その単位への書き込みは行わず、上記 (A) 前提不一致と同じ扱いで
このスコープを narrow fallback へフォールバックする（§3.2 の統一規則を
そのまま適用し、新しいフォールバック粒度の規則を追加しない）。この
再検証は「対象スコープの検証を書き込み開始直前に 1 回行う」という
当初の記述（旧稿）を撤回し、「対象スコープ内の**各**書き込み単位の
直前に行う」へ改訂したものである。

**検証コストの増分（§4 と対応させる正直な開示）**: この改訂により、
1 つのスコープ（子数 `k`）に対する `child_handles` 呼び出し回数は
「スコープ開始時に 1 回」から「書き込み単位ごとに 1 回（最大 `k` 回）」
へ増える。`child_handles` の実装が親の子ノード列を毎回フルスキャンする
場合、1 スコープあたりの検証コストは `O(k)` 回の呼び出し × 呼び出し
あたり `O(k)` の走査で最悪 `O(k²)` となり、§3.2a が当初想定していた
「アイテム 1 件・部分木 1 件あたり高々 1 回の走査」という前提から後退
する。この後退を正直に認めたうえで、次の理由により許容する: (1) `k` は
**keyed list アイテム 1 件の子ノード数**（または子孫の部分木 1 件の
子ノード数）に閉じたローカルな値であり、keyed list 全体の要素数（`n`）
には依存しない。実測ワークロード（親 #1371 の `tr > td > text`）のように
アイテム内の子ノード数が定数に近い構成では実質 `O(1)`（呼び出し回数も
走査コストも定数）のままである。(2) この再検証はいずれも Rust 側の
値比較のみで完結し（`child_kind`/`as_element`/`tag_name`/`text_data` は
いずれも読み取り専用の観測であり web-sys 境界への書き込みを伴わない）、
§3.2 が既に許容している「Rust 側の比較コストは安価」という前提の範囲内
に収まる。(3) この再検証を経ずに stale ハンドルへの書き込みを許すことは
§6.1 の収束契約そのものを破る安全性上の欠陥であり、性能とのトレード
オフではなく必須の是正である。§4「コンテキスト消費」への影響はなし
（新しいトレイト・メソッド・データ構造を追加せず、既存 `ChildNodeDom`
の各メソッドを呼ぶ回数・タイミングを変えるのみ）。

- **native 単体テストでのモック方法**: 既存モック（`type Handle = String`、
  アイテムキーを表す文字列）と同型に、`type ChildHandle` もモックの
  内部ツリー表現上の位置を指す不透明な値（例: `String` のパス表現や
  連番 `usize`）として実装できる。§7 の native 単体テスト計画（決定的な
  適用計画の固定）はこのモックへ発火順序制御を注入する形で構成する。
- この新設は §4 コンテキスト消費軸の評価（改訂版を参照）における
  「新規トレイト・新規モジュールの追加は最小限にする」という方針の
  範囲内である: 追加するのは 1 トレイト・1 ハンドル型・1 列挙型・5 メソッド
  のみで、汎用 reconciliation が要する仮想ツリー・差分アルゴリズムには
  当たらない（本改訂で undo ログ用の `live_attrs` を撤回したため 5 → 4
  メソッドへ削減した後、PR #1395 codex-review 指摘スレッド 2 対応で
  ライブ Text 値読み取り専用の `text_data` を追加したため 4 → 5
  メソッドへ再度増加した。§3.2a・§6 参照。増減いずれも既存の「最小限」
  方針の範囲内であることは、追加のたび §4 で個別に再確認する）。

### 3.3 (b) 束縛点限定更新を不採用とする理由

- core 側 API 面の拡張（アイテム内束縛点の明示宣言）とユーザー向け

  API（`crates/core/src/keyed.rs`）へ新しい宣言構文を追加する判断は、
  本イシューが対象とする「wasm-client 内部の適用最適化」の範囲を超える。
- Phase 3 #1384「アイテムの構造同型判定と束縛点パス導出（core 側）」と
  技術的に重複する。(b) を先取りして本イシューで確定すると #1384 の
  設計余地を狭めるため、将来の拡張経路として関係を明記したうえで
  本イシューでは見送る。
- 併用案（(a) を既定とし (b) を明示宣言時のみ優先）も、(b) 自体を見送る
  ため単独では成立せず不採用とする。

## 4. §3.1（`intentional-non-adoption.md`）整合の論証

Update op 設計書 §5 の 4 軸論証を継承・拡張し、本書の適用手段の変更
（§3.2）が同じ結論に留まることを確認する。

- **明示性**: 対象は `data-key` で確定済みのキー 1 件（`KeyedOp::Update`
  の対象アイテム）の中身に閉じる。アイテムがどの keyed list 配下にある
  かは既存の `grep -r 'data-bind-list\|data-key'` の明示性から変わらない。
  探索的 reconciliation（どのノードとどのノードを対応付けるかを推定する
  処理）を一切持たない。
- **決定性**: 比較は位置対応（インデックス同順）+ `PartialEq` のみで
  行う。ヒューリスティック（key 推定・ノード移動推定・最長共通部分列等）
  を一切導入しない。同一の新旧アイテム対に対し、適用される per-child
  操作列（`set_data` / 属性差分 / 部分木フォールバック のいずれか）は
  常に一意に決まる。
- **機械検証可能性**: 純粋層（`keyed_apply.rs`）の適用計画算出は
  `ChildExchangeDom` と同型のトレイト抽象、および §3.2a で新設する
  `ChildNodeDom` と同型のトレイト抽象でモック注入できる native 単体
  テストにより、どのインデックスにどの操作が選ばれるかを決定的に
  固定できる（§6・§7 テスト計画参照）。
- **コンテキスト消費**: 汎用 diff アルゴリズム（reconciliation）のような
  新規の大きな抽象層を追加しない。既存 2 層構成
  （純粋層 + wasm32 配線層）への差し込みに留まり、`replace_item_children`
  の実装を置き換えるのみで新規トレイト・新規モジュールの追加は最小限
  （§7 参照）にする。既存 `KeyedListDom` のメソッド・シグネチャは 1 つも
  変更しない。ただし子孫の Text/Element ノードへ直接到達する走査手段が
  既存トレイトにないため、§3.2a で新設する `ChildNodeDom`（1 トレイト・
  1 ハンドル型・1 列挙型・5 メソッド）を追加する（旧稿は「既存シグネチャの
  流用のみで済む」としていたが、これは誤りであり本改訂で撤回する。
  codex-review 指摘、PR #1395 スレッド 1 対応）。§6 が確定する 3 段
  エスカレーション（段 1 narrow fallback → 段 2 item 全置換 → 段 3
  `resync_required`）は、段 2 に既存の `create_item`/`replace_root`
  （タグ不一致時のアイテム全置換、§2 手順 2）を**そのまま再利用**し、
  段 3 に既存の `resync_required` 契約（PR #1391/#1392 で確定済み）を
  **そのまま再利用**するため、新しいデータ構造・新しい DOM 操作
  プリミティブは 1 つも追加しない。**この「新しいデータ構造を追加しない」
  という評価はアイテムキー粒度の話であり、内部表現の path 粒度化までは
  含まない点を明示的に留保する**（本改訂で追加、P1-1 対応）:
  `ApplyOutcome::achieved_attrs`（`crates/wasm-client/src/keyed_apply.rs`）
  は現行実装ではアイテムキー 1 本につき `Vec<(String, String)>` 1 件を
  持つフラットな `HashMap<String, Vec<(String, String)>>` であり、これは
  アイテムルート 1 箇所のみが `sync_attrs` を呼ぶ現行の（#1381 以前の）
  Update op 適用を前提にした形である。本書 §3.2 規則 3 が導入する子孫
  再帰では、1 個のアイテム内で複数のスコープ（アイテムルート・任意深さの
  Element）がそれぞれ独立に `sync_attrs` を呼びうるため、達成属性を
  アイテムキーのみで区別するこの現行の内部表現では、どのスコープの
  結果かを区別できない。**この内部表現をアイテムキー粒度のまま維持する
  か、スコープ（path）粒度へ拡張するかは、本書では確定せず #1381 の実装
  判断に委ねる**（例: `HashMap` のキーをアイテムキーとスコープ path の
  組にする、達成 Node のツリー traversal 中に直接埋め込む、等はいずれも
  実装内部の選択肢であり、`ChildNodeDom`／`KeyedListDom` の公開シグネ
  チャや DOM 操作プリミティブの追加を要しない範囲に収まる限り、本節の
  「新しい DOM 操作プリミティブを追加しない」という結論とは独立である）。
  （当初 undo ログ方式・その後の再帰的
  スコープエスカレーション方式を順に検討したが、いずれも達成できない
  復元を要求する構造的な欠陥・失敗時の巻き戻し先の定義不能という欠陥が
  あったため、本改訂で撤回した。PR #1395 codex-review 継続指摘対応、
  詳細は §6 参照）。エスカレーションを「一つ外側のスコープへ再帰的に
  波及させる」という当初の設計（旧稿）はむしろ本改訂で撤回し、「段 1 の
  narrow fallback が失敗した時点で、中間スコープを経由せず既存の item
  全置換（段 2）へ直行する」というフラットな 2 段構成へ単純化した。
  これにより §6 が導入する制御フローは、既存の `build_dom_node`／
  `exchange_children`／`sync_attrs`／`create_item`／`replace_root`
  呼び出し、および `ChildNodeDom` の各メソッドを**それぞれ独立に**
  呼び出す構成にとどまり、複数スコープにまたがる再帰的なブックキーピングを
  一切持たない（新規の大きな抽象層を追加しないという評価軸の結論は、
  新設トレイトを 1 個加え、かつ制御フローを単純化してもなお成立すると
  再確認する）。`ChildNodeDom` はキー付きリストの構造変化
  （Insert/Remove/Move）を一切扱わず、既存の位置対応
  （インデックス同順）比較の結果を実 DOM へ反映する経路の拡張に閉じる
  ため、汎用 reconciliation が要する仮想ツリー・差分アルゴリズム・新規
  抽象層のいずれにも当たらない。

**Update op 設計書 §3.2 c 案「深さ 1 打ち切り」との関係（撤回の宣言）**:
本書 §3.2 の per-child 規則は、新旧の種別・タグが同型と確認できる限り
子孫のさらに内側へも同じ規則を再帰適用する。これは c 案が当初定義した
「子孫のさらに内側だけを選択的に更新する再帰比較は行わない」という
深さ 1 打ち切りと文字どおり矛盾するため、本書はその打ち切り定義を
**正式に撤回・改訂**する（§1・§3.2-4 で確定）。撤回する理由: 実測対象
（親 #1371 の CSR ベンチワークロード、`bench/csr/fandhe/src/lib.rs`）の
アイテムは `tr > td > text(label)` であり、更新対象の Text ノードは
アイテムルート直下ではなく孫（`td` の子）に位置する。深さ 1 打ち切りを
維持したまま「浅い」子ノード diff をアイテムルート直下限定で行うと、
`td` 要素が「変更あり」の一括判定を受けて丸ごと再構築され、`set_data`
に到達しない。本書冒頭 §1 の目的（テキスト 1 文字変更を `set_data` 1
回へ帰着させる）を実測ワークロードで達成するには、深さ 1 打ち切りの
撤回が構造的に必須であり、任意の設計判断ではない。

**Update op 設計書 §3.2 d 案（却下済みの再帰 diff）との境界線**: 撤回
するのは「再帰する深さ」のみであり、d 案の却下根拠とは独立した軸である
ことを次で確認する。d 案の却下対象は「新旧ノードの任意位置への最小
パッチを探索する morphdom 型汎用 diff」（例: key のないノード列に対する
最長共通部分列やノード移動の推定）である。本書 §3.2 は「位置が新旧で
同一（インデックス同順）かつ種別・タグが値比較で一致するときに限り」
成分ごとの最小書き込みへ進み、1 箇所でも前提が崩れれば即座に（その
不一致が発生した子ノード列を持つ要素のみを対象に）フォールバックする。
探索も並べ替えもキー推定も行わない点が d 案との本質的な差であり、
d 案の却下理由（ヒューリスティック性・非決定性・任意深さの
reconciliation）はいずれも本書の方式には当てはまらない。「深さ 1
打ち切り」の撤回と「d 案が却下されたヒューリスティック性・非決定性」
は独立した軸であり、前者を撤回しても後者は一切持ち込まれない。

**再評価トリガー充足確認**: 本設計は `intentional-non-adoption.md` §3.1 の
仮想 DOM再導入提案に該当しない（keyed list Update op 専用経路の内部
最適化であり、対象範囲・判定方式は上記で確認したとおり非探索的・
決定的である。「深さ 1 打ち切り」を撤回した点は Update op 設計書 §3.2
c 案の当初定義からの意味論改訂であって、仮想 DOM 的な汎用 reconciliation
の再導入ではない）。§3.1 の再評価トリガー（perf-browser ゲートでの
REQ-11 受け入れ基準の恒常的未達）には依拠せず、本設計の採否判断は
親 #1371 の実測結果のみを根拠とする。この結論は PR 本文にも明記する
（`.claude/rules/coding-rust.md` の必須要件）。

## 5. 同値スキップの層の契約

- 前回値比較（Text の値同値判定・Element のタグ/属性同値判定・子数/
  種別判定のいずれも）は**Rust 側の純粋層**（`keyed_apply.rs` の適用
  計画算出）で行い、比較自体は web-sys 境界呼び出しを一切経由しない
  ことを契約とする。比較の根拠は達成 Node キャッシュ（`old_items`／
  `compose_achieved_children` が維持する旧 `Node`）に限定する。
- **Text 同値スキップは §3.2a のライブ整合チェック（本改訂で追加した
  4・5 点目）を通過した後にのみ成立する（本改訂で明記、PR #1395
  codex-review 指摘スレッド 2 対応）**: 上記の「比較自体は web-sys
  境界呼び出しを一切経由しない」契約は、per-child 規則そのもの
  （どのノードに何を書き込むか、または同値としてスキップするかの
  決定）が達成 Node キャッシュ由来の値比較のみで行われることを指す。
  一方、その決定を**信頼してよいか**（キャッシュ前提がライブ DOM 上
  でも成立しているか）は書き込み開始前に §3.2a のライブ観測で別途
  検証する。Text 位置でライブ値がキャッシュの旧値と乖離している場合
  （hydrate 由来の初期値ドリフト・外部コードによる直接書き換え等）は
  §3.2a 5 点目により該当スコープが (A) 前提不一致としてフォールバック
  し、新しい `Node` から作り直すことで同値スキップに起因する未収束を
  防ぐ。つまり「新旧が同値ならスキップ」という決定自体はキャッシュ
  比較のみで一意に決まる（決定性は保たれる）が、その決定が実際に
  適用されるのはライブ値がキャッシュの旧値と一致している場合に限られる。
- **cache-miss 経路（`stale_update_keys` 由来ではなく、保持キーに対応
  する直前の `Node` がキャッシュに存在しない場合。プレースホルダ旧
  `Node` が渡される経路）では per-child diff を行わず、必ず従来の
  detached 構築 + `exchange_children` へフォールバックする**（不変条件。
  §2 で確認した既存の「ルート要素タグ一致判定をライブ DOM 照会にする」
  判断と同じ理由: プレースホルダの内容は per-child 差分の根拠にならない）。
  **この forced な `replace_item_children` 呼び出しは、本書 §3.2・§6 の
  per-child diff・3 段エスカレーションのいずれの対象でもない**（本改訂で
  明記、P1-2 対応）: per-child diff は達成 Node キャッシュに実内容がある
  ことを前提とする比較駆動の仕組みであり、cache-miss はその前提を欠くため
  比較を一切行わず既存の `replace_item_children`（§2 手順 3・4）を無条件に
  呼ぶだけの、#1330/#1340 で確立済みの**別経路**である。cache-miss 経路と
  per-child diff 駆動の段 1 (A) narrow fallback はいずれも同じ
  `replace_item_children` API を呼ぶ点で実装を共有しうるが、「比較の
  結果として narrow fallback へ入ったのか（段 1→段 2→段 3 の対象）」と

  DOM を直接読み出す構造フォールバックへ委ねる」という以前の記述は、

- #1382（`sync_attrs` の属性値同値スキップ）との責務分担: #1382 は

## 6. セキュリティ不変条件・関連文書との整合

- **REQ-1（既定エスケープ）**: `set_data` は `CharacterData.data` プロパティ
  への文字列代入であり、DOM 標準上 HTML パースを一切伴わない（`innerHTML`
  系 API を新設しない）。`RawHtml` ノードへ子孫が到達する経路は、
  §3.2 で述べたとおり既存の `build_dom_node` の fail-closed 契約（構築
  失敗 → `None` → 部分木を detached 構築 + 交換へフォールバック）を
  継承し、新しい迂回経路を作らない。
- **属性検証規則の共有**: Element ↔ 同タグ Element の属性差分適用は
  Update op 設計書 §3.2 c 案・§6 不変条件 2 が定める既存の `sync_attrs`
  検証規則（URL スキーム・`srcset` 候補分割・イベントハンドラ属性
  `on*` のブロック）をそのまま再利用する。検証規則を複製しない。

### 6.1 構造的原子性契約とトレードオフ（本改訂で全面確定）

**経緯（PR #1395 codex-review 継続指摘対応）**: 本書は codex-review で
2 件の P0 指摘を経ている。(P0-1) `sync_attrs` による Element 自身の
属性書き込み失敗は、その Element の子ノード列交換では修復できない。
(P0-2) narrow fallback 自体が失敗した場合の巻き戻し先が「Update 開始前
の状態」ではなく「フォールバック試行直前の（一部新しい）部分適用状態」
であり、旧のままか新のままかの二値契約が破れる。これに先立つ旧稿
（undo ログ方式）も、`sync_attrs` の部分達成判定が曖昧・`set_text_data`/
属性 undo の失敗が終端バックストップの対象外・部分木 undo がライブ専用
状態を復元できない・ライブ子ノード列とキャッシュの乖離を検出できない、
の 4 件の指摘で撤回済みである。本改訂は、これら計 6 件の指摘がいずれも
「失敗をこのスコープ・一つ外側のスコープという単位で個別に扱い、逐次的
に巻き戻す／作り直す」という**段階的な再帰構造**そのものに起因すると
判断し、再帰構造を撤回して深さに依存しない**フラットな 3 段エスカレー
ション**（段 1 → 段 2 → 段 3、中間スコープでの再試行なし）へ置き換える。

**本書が保証しない事項の明記**: 本書は「Update op 適用の結果、item の
ライブ DOM が Update 開始前の状態（旧）と Update 完了後の状態（新）の
いずれか一方に厳密に一致する」という**二値原子性を保証しない**。段 1
の書き込み単位を複数回・独立に呼び出す設計である以上、途中失敗時の
ライブ DOM は「一部が新しい値、一部が旧の値」という中間状態を取り
うる。旧方式（`replace_item_children` による item 単位の detached
構築 + 全交換 1 回のみ）が持っていた二値原子性を、本書は意図的に
「過渡的な観測可能性」へ緩和する。この緩和と引き換えに得るものは
書き込み量の削減（テキスト 1 文字変更を `set_data` 1 回へ帰着させる、
§1 の目的）である。

**本書が保証する事項**: 上記の緩和と引き換えに、次の 3 点は不変条件
として保証する。

1. **安全性**: 中間状態を含むいかなる時点のライブ DOM も、既定
   エスケープ・属性検証規則を迂回した値を一切含まない。ある時点で
   ライブ DOM 上に存在する属性値は、`sync_attrs` の検証（URL スキーム・
   `srcset` 候補分割・`on*` イベントハンドラのブロック）を旧レンダー
   または新レンダーいずれかの適用時に通過済みの値のみである
   （`sync_attrs` は検証を通過した属性のみを書き込む契約であり、部分
   達成であっても書き込まれた個々の属性は必ず検証済み）。Text の
   `set_data` は `CharacterData.data` への文字列代入であり、DOM 標準上
   HTML パースを一切経由しない。したがって中間状態はいかなる形でも
   XSS 安全性を損なわない。
2. **fail-closed なエスカレーション**: いかなる失敗経路（段 1 の (A)
   narrow fallback 失敗、段 1 の (B) 書き込み失敗、段 2 の item 全置換
   失敗）でも、同一 Update op 適用（同一 `apply_ops_with_items` 呼び出し）
   の中でより広い範囲の新規構築（段 1 narrow → 段 2 item 全体）へ前進し、
   それも失敗すれば既存の確立済み `resync_required` 契約（PR #1391/#1392、
   リスト全体の構造フォールバック）へ合流する。後退（成功済みの書き込み
   を個別に「戻す」処理）は一切行わない。
3. **収束の範囲と時期の正直な区別**（本改訂で訂正、PR #1395 codex-review
   10 巡目 P0・12 巡目 P0・13 巡目 Bugbot High 対応）。**不変条件
   （正確化版、3 値）**: 呼び出し元（`crates/wasm-full` の
   `commit_keyed_list_result` 相当）にとっての 1 回の更新サイクル（1 回の
   `dispatch`／`apply_update_for_dirty` 呼び出し）が終了した時点で、当該
   keyed list フィールドは次のいずれかの確定状態にある: (a) 新しい view
   （意図した内容）へ収束済み（段 1・段 2 の成功、または段 3 到達後の
   即時再同期の成功）。(b) 旧 view（Update 開始前の内容）のまま無傷で
   確定（`ResyncRequired` が**ライブ DOM への書き込みを 1 件も行わずに**
   到達した「no-touch」経路。詳細は下記「`dom_mutated` 判定」参照）。
   (c) 空（段 3 到達後、ライブ DOM が変更済みの状態で即時再同期も失敗した
   場合のクリア終端、下記参照）。新旧混在の部分適用状態がこの更新サイクル
   の境界を越えて持ち越されることはない（クリア終端自体がさらに失敗する
   二重障害の場合を除く。この例外は保証の撤回ではなく前提条件の明示で
   あり、詳細は下記参照）。**(b) と (c) を区別する理由**: `ResyncRequired`
   は「達成 Node を確定できない」という一点のみを表す信号であり、その
   時点でライブ DOM が実際にどの状態にあるか（無傷の旧 view のままか、
   一部書き込み済みの中間状態か）を区別しない。無傷の旧 view のまま残る
   `ResyncRequired`（例: 上限超過・非 `Element` view・detached な構築
   失敗等、ライブ DOM への書き込みを一切試みる前に判明する契約外入力の
   拒否）に対してまで一括クリアを適用すると、破損していない健全なリスト
   を不必要に消去してしまう（本改訂で是正、PR #1395 codex-review 13 巡目
   Bugbot High 対応。以前の版は `ResyncRequired` を無条件でクリア終端の
   対象としており、この区別を欠いていた）。以下、この不変条件が成立する
   経路を詳述する: 段 1→段 2 のエスカレーションは
   同一 `apply_ops_with_items` 呼び出し内で完結し、観測可能な中間状態は
   その呼び出し内のごく短い過渡期間に限られる。段 2 も失敗し段 3
   （`resync_required`）へ到達した場合、`apply_ops_with_items` 自体は
   この呼び出し内では収束しない（ライブ DOM は段 2 の失敗試行直前の状態
   〔中間状態を含みうる〕のまま残る）が、**呼び出し元（`crates/wasm-full`
   の `commit_keyed_list_result` 相当）は、次回の `dispatch`／dirty 化を
   待たず、`resync_required` を受け取った同一更新サイクル内で直ちに
   `resync_required` の対象フィールドについて 1 回、DOM 読み出しベースの
   構造フォールバック（既存の cache-miss 分岐と同じ
   [`crate::keyed_dom::apply_keyed_list`] 経路）を実行する**。これにより
   部分適用状態がこの呼び出し境界の外（次回の `dispatch` まで）へ持ち
   越されることはない。**以前の版は「収束は次回の適用実行時点で確定
   する」としていたが、これは誤りであり撤回する**: 旧稿の記述は
   `resync_required` を受けた呼び出し元がキャッシュ entry を削除する
   だけで、実際の修復はその後 dirty になった場合の cache-miss 分岐に
   委ねられるという実装（`crates/wasm-full/src/lib.rs::commit_keyed_list_result`
   の `ResyncRequired` アーム、`crates/wasm-full/src/lib.rs::apply_update_for_dirty`
   の cache-miss 〔`None`〕分岐）を前提としていたが、これでは state が
   再び dirty 化されるまで新旧混在の DOM が無期限に残りうる（PR #1391/
   #1392 が確立した `resync_required` 契約自体は「次回はライブ DOM を
   直接読み出す」という**経路の選択**を保証するのみで、次回の到来
   〔dispatch の再発生〕そのものは保証しない）。本改訂は、この即時
   再同期呼び出しを段 3 の契約そのものへ格上げすることで、この持ち越し
   を解消する（実装詳細・回帰テストは §7 参照）。
   - **`dom_mutated` 判定（本改訂で新設、PR #1395 codex-review 13 巡目
     Bugbot High 対応）**: `KeyedListApplyResult::ResyncRequired`
     （および `apply_ops_with_items` が返す `ApplyOutcome`）へ、この
     適用試行で**ライブ DOM への書き込みが 1 件でも実行されたか**を表す
     `dom_mutated: bool` 相当のフィールドを追加する（具体的な API 形状
     ―― `ResyncRequired` variant への直接追加か、`ApplyOutcome` から
     `KeyedListApplyResult` 変換時に導出するか ―― は #1381 の実装判断に
     委ねる）。**分類原則**: `dom_mutated = false` となるのは、ライブ
     DOM への書き込み（`setAttribute`/`removeAttribute`/`set_text_data`/
     `insertBefore`/`removeChild`/`appendChild` 等の web-sys 境界呼び出し）
     を 1 件も発行する前に `ResyncRequired` が確定する経路に限る。具体例
     （実コードで確認済み、`crates/wasm-client/src/keyed_dom.rs` 参照）:
     `new_list_node`/`previous_list_node` が契約外の非 `Element` 形状
     （1213・1405・1565・1570 行）、`diff_keyed_items` の上限超過検証
     （§2 参照、diff 計算自体を行わず `dom` に一切触れない）、`list_element`
     の親要素不在（1133 行）、コンテナ自身のタグ変更時の detached 構築
     失敗（`build_dom_node_with_namespace` が `None`、1142 行）。これら
     以外の `ResyncRequired`（段 1 の書き込みを 1 件以上試みた後に段 2 も
     失敗した経路、cache-miss + `stale_update_keys` 変換〔§5 参照。この
     経路は他の保持キーが実際に丸ごと新規構築されライブ DOM が変化して
     いる可能性があるため、既定は `dom_mutated = true` とする〕を含む）
     は `dom_mutated = true` として扱う。判定に迷う場合は
     `dom_mutated = true`（より安全側、後述のとおり mutated 側は
     no-touch 側より過剰動作のリスクが小さいクリア終端で決着する）に
     倒す。
   - **即時再同期は 1 回のみ実行し、再帰的リトライはしない**。即時
     再同期自体は `dom_mutated` の値に関わらず試みてよい（no-touch
     経路でも、収束を早められる機会があれば活かす。詳細は次項）。
   - **即時再同期自体が実行時に失敗した場合（`dom_mutated` で分岐、
     本改訂で追加・13 巡目で拡張、PR #1395 codex-review 12 巡目・13 巡目
     P0/Bugbot High 対応）**:
     - **`dom_mutated == true`（ライブ DOM が変更済みの状態、従来どおり
       クリア終端）**: 以前の版は「キャッシュ entry が不在のまま終わり、
       修復は次回 dirty 時の自己修復ループに委ねられる」としていたが、
       これは §6.1 冒頭で問題視した「次回の到来〔dispatch の再発生〕は
       保証されない」という状況をこの終端で再び許してしまう誤りであり
       撤回する。呼び出し元は**同一更新サイクル内で直ちに、当該
       フィールドの keyed list コンテナ全体を [`KeyedListDom::clear_children`]
       （`web-sys` 実装では `set_text_content(None)` の単一呼び出し。
       PR #1391 でマージ済みの全キー削除一括 clear 経路プリミティブの
       再利用であり新しい DOM 操作プリミティブを追加しない）で一括
       クリアし、リストを「空」という確定状態へ倒す**。設計根拠:
       (i) 新旧混在の DOM を無期限に表示し続けるより、空リストという
       一貫した確定状態のほうが fail-closed である（誤ったデータ・
       部分的に古いデータが利用者へ表示され続けることを防ぐ）。
       (ii) `clear_children` は最粗粒度・単一 DOM 呼び出しであり、
       複数ステップから成る再構築（即時再同期の `apply_keyed_list`
       自体）よりも失敗面が最小（`set_text_content` 1 回の成否のみに
       帰着する）。(iii) クリア後は達成 Node キャッシュの entry が
       存在しないため、次回 dirty 到来時は既存の cache-miss 分岐が空
       コンテナから keyed list 全体を再構築する（既存の自己修復ループと
       同一経路であり、新しい回復メカニズムを追加しない）。
     - **`dom_mutated == false`（ライブ DOM は Update 開始前の旧 view の
       まま無傷、本改訂で追加、PR #1395 codex-review 13 巡目 Bugbot High
       対応）**: この場合は**クリアしない**。旧 view は既に確定状態
       （上記不変条件 (b)）であり、新旧混在は存在しないため「持ち越し
       禁止」の不変条件に抵触しない。呼び出し元は達成 Node キャッシュの
       entry を不在（未確定）のままにし、修復は次回 dirty 時の
       cache-miss 自己修復ループへ委ねる（無傷のリストをクリアで壊す
       ことは fail-closed の趣旨に反するため、あえて何もしない選択が
       正しい）。
   - **クリア終端自体が実行時に失敗した場合の残余（`dom_mutated == true`
     の分岐にのみ存在する。`dom_mutated == false` はそもそもクリアを
     試みないため、この残余リスクの対象外）**: `clear_children`
     （単一の `set_text_content` 呼び出し）すら失敗する環境は、DOM への
     一切の書き込みが不能な状態であり、初回レンダリングを含むあらゆる
     描画が構造的に不能な環境異常に相当する。この場合に限り、キャッシュ
     entry が不在（未確定）のまま処理が終わり、修復は次回 dirty 時の
     自己修復ループへ委ねられる（すなわち、以前の版が「即時再同期失敗
     時の唯一の終端」としていた挙動は、クリア終端自体の失敗という
     **二重障害**の場合にのみ残存する残余リスクへ格下げされる）。
     `unwrap()`/`panic!` は使わず、固定英語文言の警告ログを出して処理を
     継続する（他の残余リスク〔`replace_root_node` の二重失敗等〕と
     同型の扱い）。

**旧方式との比較（トレードオフの明示）**: 旧方式（item 単位の detached
構築 + 全交換 1 回のみ）は二値原子性を持つが、1 文字のテキスト変更でも
item 全体の子ノード列を作り直す。新方式は二値原子性を過渡的観測可能性
（上記 3 点の不変条件のもとでの中間状態の存在）へ緩和し、その代償として
書き込み量を削減する。安全性の不変条件（既定エスケープ・fail-closed
エスカレーション）はいずれの方式でも維持される。

### 6.2 3 段エスカレーションの詳細

1. **段 1（最小差分 in-place 書き込み）**: §3.2 の per-child 規則に従い、
   Text の `set_data`・Element の `sync_attrs` を個別に呼ぶ。
   - **(A) 前提不一致**（§3.2a のライブ観測含む）が起きたスコープでは、
     そのスコープ自身（要素自身の識別子・属性には触れず、子ノード列
     のみを対象とする）へ narrow な detached 構築 + 交換
     （`replace_item_children`。アイテムルート・任意深さの Element の
     いずれでも同一 API を再利用する。§3.2a 参照）を試みる。**成功**
     すれば、このスコープを含むアイテム内の他のスコープの処理は影響を
     受けず継続する。**失敗**すれば、このスコープに閉じた再試行や
     一つ外側のスコープへの段階的な波及は行わず、アイテム全体について
     残る段 1 処理をすべて打ち切り、直ちに段 2 へ進む。
   - **(B) 書き込み失敗**（`set_text_data` が `false` を返す場合、または
     `sync_attrs` の戻り値が§3.2「(B) 書き込み失敗」の定義どおり**「ポリシー
     拒否を除いた期待 achieved 集合」**と一致しない場合）が起きた場合、
     その Element・Text 自身への narrow fallback は**一切試みない**
     （P0-1 の再発防止: Element 自身の属性書き込み失敗は、その Element を
     子として含む親スコープの子ノード列交換でしか本質的に修復できず、
     その Element 自身の子ノード列交換〔narrow fallback〕では属性に触れ
     られないため）。**ポリシー拒否（`is_attr_write_rejected` が
     `true` のエントリの skip）自体は (B) に該当しない**（本改訂で明確化、
     P0 対応。危険 URL スキーム・`srcset`・イベントハンドラ属性の意図的
     skip は仕様どおりの挙動であり、`crates/wasm-client/src/keyed_apply.rs`
     の既存テスト `compose_achieved_children_keeps_old_value_when_attr_update_is_rejected`／
     `compose_achieved_children_omits_attr_when_new_attr_addition_is_rejected`
     が固定する「拒否時は旧安全値を保持し op 自体は計画どおり適用できて
     いる」契約と矛盾させない）。(B) と判定された時点で、アイテム全体に
     ついて残る段 1 処理をすべて打ち切り、直ちに段 2 へ進む。
2. **段 2（item 丸ごと差し替え）**: §2 手順 2 が既に定義するタグ不一致
   時の既存経路（`KeyedListDom::create_item` による detached 構築 →
   `KeyedListDom::replace_root` によるルート要素の差し替え）を、タグ
   一致・段 1 のいずれかの失敗という**新しいトリガー条件**でも呼び出す
   （新しい DOM 操作プリミティブを追加せず、既存経路の発火条件を拡張
   するのみ）。**この「タグ一致でも呼び出す」拡張が、§1・§3.2 規則 4 で
   確定するアイテムルート要素の DOM ノード同一性契約を狭める**（本改訂
   で明記、P0 対応）: c 案・§3.2 規則 4 が定めるルート同一性維持は、
   タグが一致し段 1 の書き込みがすべて成功するハッピーパスに限られ、
   段 1 のいずれかの単位が実行時に失敗し段 2 が発火した場合（タグは
   一致していても）はルート要素自体が新しい要素へ差し替わる。**影響
   範囲を正直に記載する**: 外部（`crates/wasm-full` 等の上位レイヤ・
   アプリケーションコード）が保持するルート要素の参照は段 2 発火後は
   失効しうる。フォーカス・選択状態（テキスト選択・カーソル位置）・
   IME 変換途中の状態は、ルート要素自体が対象の場合は失敗経路で失われる
   （更新設計書 §3.3 が定めるフォーカス保持契約の対象は「ルート要素は
   保持されたままの子孫の変更」であり、ルート要素自体が差し替わる場合は
   その前提が成り立たない）。**発動条件・頻度**（本改訂で訂正、PR #1395
   codex-review 9 巡目 P1 対応。以前の版は発動条件を (B) のみに限定して
   おり、§6.2 段 1 (A) が定める「narrow fallback 自体の実行時失敗も段 2
   へ進む」という別の発火条件を見落としていた）: 段 2 は次の**いずれか**
   で発火する。(i) 段 1 (B) の書き込み実行時失敗（`setAttribute`/
   `removeAttribute`/`set_text_data` の `Err`・`false`）。(ii) 段 1 (A) の
   narrow fallback（`replace_item_children`、子数・種別・タグの通常の
   構造変更に対しても試みられる detached 構築 → 交換）自体の実行時失敗
   （構築失敗・`exchange_children` の部分失敗）。**(ii) は「子数・種別・
   タグが変わる」という通常のデータ更新そのものでは発火しない**（narrow
   fallback はそうした構造変更に対して常に試みられ、多くの場合成功して
   段 2 まで進まずに完結する。段 2 へ進むのは narrow fallback という
   DOM 操作自体が失敗した場合に限る）。(i)・(ii) いずれも DOM 操作の
   実行時失敗（例外的な `Err`・`false`）を要し、通常のデータ更新（構造
   変更の有無を問わず narrow fallback が成功する経路）・ポリシー拒否
   （危険 URL スキーム・`srcset`・イベントハンドラの意図的 skip、§3.2
   「(B) 書き込み失敗」参照）だけでは発火しない。実 DOM 上の
   `setAttribute`・`insertBefore`・`removeChild` 等は通常成功する操作で
   あるため、段 2 の発動は稀な異常系に限られる（旧方式の全再構築でも、
   タグ不一致時は同じ `create_item`+`replace_root` 経路を通っており、
   ルート同一性が失われる場面自体は既に存在していた。本書が新たに広げる
   のは「タグが一致していても実行時失敗があれば同じ
   経路を通る」という発火条件のみである）。`create_item` は新しい `Node`
   （`new_node`、キャッシュ
   ではない）から detached に構築するため、失敗しても呼び出し時点まで
   ライブ DOM には一切触れない（既存契約）。`replace_root_node` は
   「新要素を挿入 → 旧要素を除去」の 2 呼び出しからなり、除去が失敗
   すれば挿入した新要素を取り除いて**この呼び出し 1 回の内部でのみ**
   挿入前の状態（段 1 の失敗試行時点でライブ DOM 上にあった旧要素。
   段 1 で一部の書き込みが既に成功していた場合はその内容を含む）へ
   ロールバックする。**この呼び出し内ロールバック契約を Update op
   全体の巻き戻し手段として流用しない**（P0-2 の再発防止: これは
   『新要素を二重に残さない』という `replace_root_node` 自身の狭い
   保証に過ぎず、段 1 で既に成功していた書き込みを消し込む・item 全体
   を Update 開始前の状態へ戻す保証ではない）。段 2 が成功すれば、item
   ルート要素を含む部分木全体が新しい `Node` の内容で新規構築された
   ことになり、段 1 の途中失敗までに存在していた部分適用状態は
   （個別に「戻す」処理を経ずに）まとめて新しい内容へ上書きされる。
   これにより P0-1 が指摘した「Element 自身の属性の部分達成状態が
   残る」経路・P0-2 が指摘した「フォールバック失敗時に部分適用状態が
   残る」経路のいずれも、段 2 の成功時には解消される。
3. **段 3（`resync_required`）**: 段 2（`create_item` の構築失敗、または
   `replace_root_node` の 2 呼び出しいずれかの失敗）も解消しなかった
   場合、当該 Update op 適用全体を「未達成」として扱い、既存の
   `ApplyOutcome::resync_required`（PR #1391/#1392 で確立済み、
   `crates/wasm-client/src/keyed_apply.rs` doc 参照）を立てる。
   `apply_ops_with_items` 自体の呼び出し内ではライブ DOM は段 2 の失敗
   試行直前の状態（中間状態を含みうる）のまま残り、呼び出し元は今回の
   適用結果を達成 Node キャッシュへ確定させない。**呼び出し元
   （`crates/wasm-full` の `commit_keyed_list_result` 相当）は、この
   `resync_required` を受けた同一更新サイクル内で直ちに 1 回、
   [`crate::keyed_dom::apply_keyed_list`]（ライブ DOM を直接読み出す
   構造フォールバック）を実行し、当該フィールドを新しい view と一致
   させる**（本改訂で段 3 の契約へ格上げ、PR #1395 codex-review 10 巡目
   P0 対応。次回の `dispatch` を待つ設計では中間状態が無期限に残り
   うるため）。**この即時再同期自体が実行時に失敗した場合、`dom_mutated`
   （§6.1 参照）が `true`（ライブ DOM が変更済み）なら同一更新サイクル内で
   直ちに [`KeyedListDom::clear_children`] による一括クリア（クリア終端）
   を実行してリストを「空」という確定状態へ倒し、`false`（ライブ DOM は
   旧 view のまま無傷）ならクリアせず旧 view を温存したまま次回 dirty の
   自己修復へ委ねる**（本改訂で追加・13 巡目で `dom_mutated` 分岐を追加、
   PR #1395 codex-review 12 巡目 P0・13 巡目 Bugbot High 対応。詳細・
   設計根拠・トレードオフ・クリア終端自体が失敗した場合の残余は §6.1
   「収束の範囲と時期の正直な区別」参照）。**`stale_update_keys`
   （現行コードの `replace_item_children` 失敗時に `apply_ops_with_items`
   が記録するフィールド、§2 手順 4）は、本書のエスカレーション設計に
   おける段 1→段 2 の合流により、**per-child diff 駆動の**（すなわち
   達成 Node キャッシュに実内容があり、実際に比較を行ったうえで narrow
   fallback へ入った）Update op 適用ラダーの終端としては使われなくなる**
   （段 1 の narrow fallback 失敗は段 2 へ直行するため）。**cache-miss
   経路（比較を行わず forced に `replace_item_children` を呼ぶ、本書
   §3.2・§6 のラダーの対象外）でこの `stale_update_keys` が非空になった
   場合は、既存の `apply_keyed_list_core`（`crates/wasm-client/src/keyed_dom.rs`
   1257〜1292 行、#1340 の fail-closed 防御）が達成 Node の合成を行わず
   `KeyedListApplyResult::ResyncRequired` へ変換する**（本改訂で訂正、
   PR #1395 codex-review 13 巡目 P0 対応。以前の版は「§2 手順 4 が定める
   現行契約〔`stale_update_keys` への記録〕のまま変更しない・本書の変更
   範囲外」としていたが、これは現行コードの記述として誤りだった。詳細は
   §5 参照）。`stale_update_keys` フィールド自体（`apply_ops_with_items`
   が記録する内部状態）は撤去を提案しないが、cache-miss 経路でこれが
   非空になったときの**呼び出し元から見た最終結果**は、本書が新しく
   定義する per-child diff 駆動の 3 段ラダーと同じく `ResyncRequired`
   （段 3 相当）であり、§6.1・§6.2 が定める即時再同期・クリア終端の
   対象に自然に合流する。

**この方式が旧稿の指摘・P0 指摘をどう解消するか**:

- finding 1（`sync_attrs` 部分達成）: 段 1 (B) の判定基準（戻り値が
  `new_attrs` とバイト等価であることのみを成功とする）により部分達成は
  即座に失敗として扱われ、narrow fallback を経由せず段 2 へ直行する。
- finding 2・3（undo 失敗・ライブ状態の復元不能）: undo という概念
  自体を持たない。段 2 は「戻す」のではなく常に**新しい `Node`** から
  作り直す。hydrate ドリフト等のライブ専用状態は、新しい要素が丸ごと
  新規生成されるため「復元すべき対象」として扱われない（既存の
  タグ不一致時 `replace_root` と同じ挙動）。
- finding 4（ライブ子ノード列とキャッシュの乖離検出）: §3.2a のライブ
  観測とキャッシュ前提の整合チェックが、per-child 書き込みを 1 件も
  開始する前に (A) 前提不一致として検出する（変更なし）。
- **P0-1**（Element 自身の属性同期失敗を子ノード交換では修復できない）:
  段 1 (B) は Element 自身への narrow fallback を試みず、直ちに段 2
  （item ルート要素ごとの差し替え）へ進むため、属性の部分達成状態は
  段 2 の成功時にまとめて上書きされる。
- **P0-2**（終端フォールバック失敗で Update の部分適用状態が残る）:
  「旧のままか新のままか」の厳密な二値原子性は前述のとおり保証しない
  （本書が明示的に撤回する契約）。その代わり、段 2 の呼び出し内
  ロールバックが「新要素の二重残存」のみを防ぐ狭い保証であることを
  明記し、Update 全体の巻き戻し手段としては扱わない。段 2 も失敗した
  場合は中間状態を含みうるライブ DOM のまま `resync_required` へ
  フォールバックし、収束は呼び出し元が同一更新サイクル内で直ちに実行
  するライブ DOM 直接読み出しに委ねる（本改訂で訂正、P0 対応。以前は
  「次回のライブ DOM 直接読み出しに委ねる」としていたが、これは次回
  `dispatch` まで持ち越されるかのように読める誤りであり、§6.1「収束の
  範囲と時期の正直な区別」が確定する即時再同期契約に合わせて訂正した。
  安全性は上記 6.1「本書が保証する事項」1 により中間状態でも損なわれ
  ない）。

### 6.3 ネストした binding キャッシュ無効化契約（段ごとの扱い）

§3.2 の narrow fallback（段 1 (A)）・段 2（item 全置換）は、いずれも
対象スコープ配下に `data-bind-list`（keyed list のネスト）が含まれる
場合、その配下の DOM ノード・ハンドルを再生成する。既存実装（アイテムの
子全体を交換した成功時）が `collect_nested_bind_list_fields(new_node)`
経由で `invalidated_nested_fields` を更新する契約を、次のとおり
一般化する。**本節の無効化契約は、子孫がネストした binding ルート
自身であるスコープ（`data-bind-list` を持つ Element）で `sync_attrs`
が呼ばれる場合、§3.2 規則 3 が定める `reserved_attr` 例外
（旧新の `data-bind-list` 値が一致する場合に限り、`data-bind-list` を
予約属性として扱い比較・書き換え対象から除外する。本改訂で条件を精緻化、
PR #1395 codex-review 11 巡目 Bugbot Medium 対応）と対をなす: 旧新値が
一致し予約属性として除外される場合、`sync_attrs` 単体では
`data-bind-list` の値は変更されず、ノードも再生成されないため、この
スコープでの通常の属性同期（narrow fallback に至らない、下記 2.）では
`invalidated_nested_fields` へ何も追加しない。一方、旧新値が**一致しない**
場合は §3.2 規則 3 のとおりこのスコープ自体が (A) 前提不一致として
narrow fallback（段 1 (A)）の対象になり、ノード再生成される。この場合は
下記 1.・3. の一般規則がそのまま適用され、`data-bind-list` を含む
新しい属性集合が反映された新ノードから field を再収集する**が、旧い
`data-bind-list` 値（旧 field 名）は新しい部分木のどこにも現れないため、
下記 1. が定める追加の扱いに従い別途無効化する**:

1. **段 1 (A) narrow fallback が成功した場合**: そのスコープの新しい
   内容（narrow fallback で構築した部分木）へ `collect_nested_bind_list_fields`
   を適用し、得られた field 集合を `invalidated_nested_fields` へ
   追加する。無効化の範囲はそのスコープ配下に閉じ、他のスコープの
   field は含めない。**このスコープが §3.2 規則 3 の `data-bind-list`
   値相違（新設ケース）を原因として narrow fallback へ入った場合は、
   上記の新しい部分木由来の field 集合に加え、旧い `data-bind-list` の
   値（達成 Node キャッシュ側 `old_attrs` から読み取れる旧 field 名）を
   明示的に `invalidated_nested_fields` へ追加する**（本改訂で追加、
   PR #1395 codex-review 11 巡目 Bugbot Medium 対応。`collect_nested_bind_list_fields`
   は新しい部分木のみを走査するため、旧 field 名は自動的には収集され
   ない。この位置での値相違を検出した時点で旧 field 名を保持しておき、
   narrow fallback 成功時に和集合として追加する必要がある。これにより、
   旧 field 用の達成 Node キャッシュ entry が新しい binding 識別と乖離
   したまま残ることを防ぐ）。narrow fallback がこの原因以外（子数・種別・
   タグの通常の構造変更、またはネストした binding を持たないスコープ）
   で発火した場合は、この追加の扱いは適用しない（新しい部分木の走査
   結果のみを使う、既存の一般規則のまま）。
2. **段 1 の `set_text_data`／`sync_attrs`（narrow fallback に至らな
   かった単位）の扱い**: これらは既存 DOM ノードを再生成しない（Text
   ノード・Element ノードの参照は保持されたまま値のみが変わる）ため、
   ネストした `data-bind-list` のノード・ハンドルは影響を受けない。
   よって `invalidated_nested_fields` へ何も追加しない。
3. **段 2（item 全置換）が成功した場合**: item 全体（`new_node`）へ
   `collect_nested_bind_list_fields` を適用し、得られた field 集合を
   `invalidated_nested_fields` へ追加する（既存のタグ不一致時
   `replace_root` 成功時の集約方式と同型）。段 1 で一部のスコープが
   既に narrow fallback で無効化を計上していた場合でも、段 2 は item
   全体を対象に改めて計上する（和集合として扱えば冪等であり、二重
   計上は実害がない）。
4. **段 3（`resync_required`）に到達した場合**: §6.1・§6.2 が確定する
   即時再同期契約により、呼び出し元が同一更新サイクル内で直ちにライブ
   DOM 直接読み出しによる構造フォールバックを実行するため、当該アイテム
   配下の nested field を**アイテム全体について保守的に**無効化する
   （どのスコープが新のまま残ったか個別に特定できないため、安全側へ
   倒す。既存の cache-miss 経路と同型の扱い）。**この即時再同期自体が
   失敗しクリア終端（§6.1・§6.2 参照）に至った場合は、当該フィールドの
   keyed list コンテナ全体が空になるため、当該フィールド配下の nested
   field を（特定のアイテムに限らず）**フィールド全体について保守的に**
   無効化する**（本改訂で追加、PR #1395 codex-review 12 巡目 P0 対応。
   クリア終端はアイテム単位ではなくリストコンテナ全体を対象とするため、
   無効化の範囲もそれに合わせて広げる）。**一方、`resync_required`
   が `dom_mutated == false`（§6.1 参照。ライブ DOM が旧 view のまま無傷）
   で到達した場合は、この段 3 到達時点の「アイテム全体について保守的に
   無効化する」規則そのものを適用しない**（本改訂で追加、PR #1395
   codex-review 13 巡目 Bugbot High 対応。ライブ DOM が一切変更されて
   いない以上、そのアイテム配下の nested field のキャッシュも実際の
   ライブ DOM と乖離していないため、無効化する対象が存在しない。即時
   再同期が成功すれば通常どおり収束し、失敗しても §6.1 のとおりクリア
   しないため、この経路では nested field の無効化は一切発生しない）。
5. 1 回の Update op 適用で複数のアイテムが独立に段 1 (A) 成功・段 2
   成功・段 3 到達のいずれかを取りうる場合、各アイテムごとに得た
   field 集合を和集合として `invalidated_nested_fields` へ集約する
   （既存の集約方式と同型）。

## 7. テスト計画（#1381／#1382 受入基準へのマッピング）

#1381・#1382 の実装時に満たすべき検証観点（本書は設計文書のため実装は
含まない）。

- **native 単体テスト（適用計画の決定的固定）**: `ChildExchangeDom` と
  同型のトレイト抽象、および §3.2a で新設する `ChildNodeDom` と同型の
  トレイト抽象へモックを注入し、次の入力に対する適用計画
  （`set_data` が呼ばれるか・属性差分の内容・部分木フォールバックへ
  切り替わるか）を決定的に固定する: (1) Text 値のみ変更、(2) Text 値が
  同値（スキップされること）、(3) 子数不一致、(4) 子の種別不一致
  （Text↔Element）、(5) 同位置 Element のタグ不一致、(6) ネストした
  Element の孫レベルでのみ不一致（段 1 (A) の narrow fallback の範囲が
  孫のみに留まり、item ルート・親レベルの他の子には影響しないこと）。
- **アイテムルート要素の DOM ノード同一性契約（ハッピーパス限定である
  ことの固定、本改訂で追加、P0 対応）**: モックの `Handle`（native モック
  では `type Handle = String` がアイテムキーを表す、§3.2a 参照）が段 1
  完了後・段 2 完了後でどう変わるかを、次の 2 ケースで対比して固定する。
  (1) ハッピーパス（タグ一致、段 1 のすべての単位が成功、または (A) の
  narrow fallback のみで完結し (B) 書き込み失敗が 1 件も起きない）では、
  `create_item`/`replace_root` が一切呼ばれず、アイテムルートの `Handle`
  （モック実装では要素参照に相当するもの）が Update 適用前後で不変で
  あることを固定する。(2) 段 1 のいずれかの単位が (B) 書き込み失敗する
  ケース（タグは一致）では、`create_item`+`replace_root` が呼ばれ、
  段 2 成功後はアイテムルートが新しい `Handle`（新規構築された要素）へ
  差し替わっており、Update 適用前の `Handle` とは異なることを固定する
  （§1・§6.2 が明記する「ルート同一性維持はハッピーパスに限る」契約の
  回帰）。
- **ライブ観測とキャッシュ前提の整合チェック（前提不一致 (A) の拡張、
  §3.2a finding 4 対応）**: 次の 5 ケースをそれぞれ個別に、書き込みを
  1 件も発生させずに該当スコープが即座に narrow fallback（段 1 (A)）へ
  切り替わることとして固定する: (1) `child_handles` の長さがキャッシュの
  旧子ノード数と不一致、(2) ある位置の `child_kind` がキャッシュの想定
  種別と不一致、(3) 種別が `Element` の位置で `as_element` が `None` を
  返す、(4)（本改訂で追加、PR #1395 codex-review 指摘スレッド 1 対応）
  種別が `Element` の位置で `as_element` は `Some` を返すが、得られた
  ハンドルへ `KeyedListDom::tag_name` を呼んだ結果がキャッシュの `i`
  番目のタグ名と不一致（例: キャッシュ上 `<span>` だがライブ DOM 上は
  `<button>`）、(5)（本改訂で追加、PR #1395 codex-review 指摘スレッド 2
  対応）種別が `Text` の位置で `ChildNodeDom::text_data` が返すライブ
  文字列値がキャッシュの `i` 番目の Text 値と不一致（新値がキャッシュの
  旧値と同値であってもフォールバックすることを含めて固定し、Text 同値
  スキップがライブ値ドリフトを放置しないことを確認する）。(6)（本改訂で
  追加、PR #1395 codex-review 11 巡目 P1-2 対応）ある位置の `child_kind`
  が `ChildNodeKind::Other`（コメントノード混入を模す）を返すケースで、
  `Text`/`Element` いずれとも一致しないため上記 (2) と同じ経路で即座に
  narrow fallback（段 1 (A)）へ切り替わり、`unreachable!()`/`panic!()`
  が発生しない（native テストがパニックなく完了する）ことを固定する。
- **書き込み単位ごとの再検証（stale ハンドル対策、本改訂で追加、PR #1395
  codex-review 11 巡目 P1-1 対応）**: 兄弟が複数（`k >= 2`）ある子ノード
  列で、単位 0（先頭の Element）への `sync_attrs` 呼び出しをモックへ
  発火順序制御で注入し、その呼び出しの**内部で**（`attributeChangedCallback`
  相当の同期的副作用を模して）親の子ノード列を書き換える（例: 単位 1
  以降のノードを削除する、または別のノードに置き換える）ケースを構成
  する。次を決定的に固定する: (1) 単位 1 への書き込み（`set_text_data`
  または `sync_attrs`）を試みる前に `child_handles(parent)` が**再度**
  呼ばれ、スコープ開始時の古いスナップショットがそのまま使い回されない
  こと。(2) 再検証が子数・種別・タグ・Text 値のいずれかの乖離を検出した
  場合、単位 1 への書き込みは 1 件も発生せず（モックの呼び出し回数で
  確認する）、このスコープが直ちに narrow fallback（段 1 (A)）へ
  切り替わること。(3) narrow fallback が成功した場合、達成 Node が
  「単位 0 の書き込み後、実際にライブ DOM 上に存在する内容」と一致し、
  stale ハンドルへの書き込みが成功したかのように誤った新状態がキャッシュ
  へ紛れ込まないこと（§6.1 の収束契約の回帰）。(4) 逆に、単位 0 の
  書き込みが後続の子ノード列に一切影響しない通常ケース（同期的副作用
  なし）では、単位 1 以降への再検証呼び出しが検出する乖離がなく、
  narrow fallback を経由せず全単位が per-child diff のまま完了すること
  （再検証の追加が通常経路の適用計画を変えないことの確認）。
- **書き込み失敗の判定と段 2 への直行（finding 1・P0-1・P0（ポリシー
  拒否分離）対応）**: (1) `set_text_data` が `false` を返すケースで、
  そのアイテムが narrow fallback を一切経由せず（この Text ノードの
  親スコープの子ノード列交換も試みずに）直ちに段 2（`create_item`+
  `replace_root` による item 全置換）へ切り替わることを固定する。
  (2) `sync_attrs` の戻り値が§3.2「(B) 書き込み失敗」の定義どおり
  **「`is_attr_write_rejected` でポリシー拒否分を除いた期待 achieved
  集合」と一致しない**（`is_attr_write_rejected` が `false` のエントリ
  について `setAttribute`/`removeAttribute` が個別に実行時失敗した部分
  達成、または `new_attrs` に存在しない名前の残存属性を含む）ケースで、
  同様にこの Element 自身の子ノード列交換を一切経由せず、直ちに段 2 へ

  （`is_attr_write_rejected` が `true` の）ケースでは、`sync_attrs` の
  戻り値が `new_attrs` と一致しなくても (B) と判定されず、段 2 が呼ばれ
  ない（narrow fallback もこの単位に対しては発生しない。段 1 のこの単位

  「(B) 書き込み失敗」の定義・既存テスト
  `compose_achieved_children_keeps_old_value_when_attr_update_is_rejected`
  の契約と矛盾しないことの回帰）。(4) 段 2 が成功した場合、部分達成の
  属性状態が最終状態としては残らず（item 全体が段 2 で構築した新しい
  `Node` 由来の内容へ完全に上書きされる）、その結果を native モックの
  最終状態から確認する。(5)（本改訂で追加、PR #1395 codex-review 9 巡目
  P0 対応）段 2 成功時の達成 Node が `new_node` そのものではなく
  `sanitize_node_for_achieved(new_node)` であることを固定する: `new_node`

  スキーム・`srcset`・イベントハンドラ属性）を 1 件含むケースで、段 1 の
  いずれかの単位が (B) 書き込み失敗し段 2（`create_item`+`replace_root`）
  が成功した後の達成 Node にその拒否属性が**含まれない**ことを確認する
  （§5「達成 Node の合成規則」の回帰。段 2 は `create_item` 自身が同じ
  検証規則で拒否するため、達成 Node に危険値が「達成済み」として紛れ込む
  経路がないことを固定する）。
- **段 2 自体の失敗と段 3 への直行（finding 2・3・P0-2 対応）**: 前項
  「書き込み失敗の判定と段 2 への直行」で構成した「単位 `k`（`k < n`）が

  固定する（段 1 (B)→段 2 への遷移そのものの固定は前項の対象であり、本項

  (1) 段 2 の `create_item` が `Node` 構築に失敗するケースでは、その
  失敗時点でライブ DOM への書き込みが 1 件も発生していないこと
  （`insert_before`/`remove` いずれも呼ばれないことをモックの呼び出し
  回数で確認する）を固定し、そのうえで `resync_required` が立つ（段 3）
  ことを確認する。(2) 段 2 の `replace_root_node` が `insert_before`

  fail-closed な合流によって解消できていることの回帰）。
- **終端の `resync_required`（finding 2・3・P0-2 対応）**: **per-child
  diff 駆動の**（達成 Node キャッシュに実内容があり、段 1 の書き込みを
  実際に試みた上で）段 2 が `create_item` の構築失敗、または
  `replace_root_node` の部分失敗のいずれかで終端まで解消しなかった
  ケースを固定する。(1) `ApplyOutcome::resync_required` が `true` に

  `ApplyOutcome::stale_update_keys` 自体は（本ケースでは段 1→段 2 の

  こと。**この非記録は「per-child diff 駆動の経路では `stale_update_keys`

  cache-miss 経路の `replace_item_children` 失敗とは無関係な独立の主張

  確定させないこと、その後に呼び出す
  [`crate::keyed_dom::apply_keyed_list`]（ライブ DOM 直接読み出しの

- **段 3 到達後の即時再同期とクリア終端（wasm-full 層、本改訂で新設・

  12 巡目・13 巡目対応）**: `crates/wasm-full/src/lib.rs::commit_keyed_list_result`

  [`crate::keyed_dom::apply_keyed_list`] を 1 回実行し、その結果で
  当該フィールドの DOM・キャッシュを確定させる。この即時再同期自体が
  失敗した場合、`dom_mutated`（§6.1 参照）が `true` なら同一呼び出し内で

  `false` ならクリアせずキャッシュ entry のみ不在（未確定）のまま旧
  view を温存する**実装へ変更する（#1381 の実装範囲、詳細な呼び出し
  シグネチャは実装時に確定する）。回帰テストとして次を固定する:
  (1) 段 3（`resync_required`）へ到達する入力（段 2 の `create_item`
  構築失敗または `replace_root_node` 部分失敗を注入したモック DOM。
  `dom_mutated == true` の代表ケース）を与えたとき、**同一の更新サイクル
  呼び出し（`apply_update_for_dirty` 1 回の呼び出し）内**で当該キーを
  含む keyed list 全体が new view（望ましい内容）と一致すること（次回の
  `dispatch`／再度の dirty 化を待たずに収束することの確認。次回
  `dispatch` が発生しなくても収束することを、テストが 2 回目の
  `apply_update_for_dirty` 呼び出しを行わずに確認する形で固定する）。
  (2)（本改訂で追加、PR #1395 codex-review 12 巡目 P0 対応）`dom_mutated
  == true` の経路で即時再同期自体が失敗する経路（モックの
  `apply_keyed_list` 相当を失敗させる注入）では、**同一の更新サイクル
  呼び出し内**で `clear_children` が 1 回呼ばれ、当該フィールドのライブ
  DOM コンテナが空（子要素 0 件）になること、新旧混在の部分適用状態が
  一切残らないこと、キャッシュ entry が不在（未確定）のまま処理が終わる
  ことを固定する（以前の版は「キャッシュ entry が不在のまま終わり、次回
  dirty 時の自己修復ループに委ねられる」としていたが、これはクリア終端を
  経ずに中間状態のライブ DOM をそのまま残す誤りであり撤回する）。
  (2b)（本改訂で追加、PR #1395 codex-review 13 巡目 Bugbot High 対応）
  `dom_mutated == false`（ライブ DOM への書き込みを 1 件も行う前に
  `ResyncRequired` が確定した入力。例: 契約外の非 `Element` view、
  上限超過、`list_element` 親不在、コンテナタグ変更時の detached 構築
  失敗を注入したモック DOM）を与えたとき、(i) 即時再同期を試みてよいが
  試みた場合は成功すれば通常どおり収束すること、(ii) 即時再同期自体が
  失敗しても `clear_children` は**呼ばれない**こと（モックの呼び出し
  回数で確認する）、(iii) 当該フィールドのライブ DOM コンテナが
  Update 開始前の旧 view のまま子要素・属性ともに一切変更されていない
  ことを固定する（無傷の健全なリストを誤って空にしてしまう回帰の防止。
  この確認が本テストの中核である）。(3)（本改訂で追加）`dom_mutated ==
  true` の経路で即時再同期・`clear_children` の**両方**が失敗する二重
  障害の経路（モックの両方を失敗させる注入）に限り、キャッシュ entry が
  不在のまま処理が終わり、修復が次回 dirty 時の自己修復ループへ委ねられる
  こと、この経路でも `unwrap()`/`panic!` が発生しないことを確認する
  （§6.1 が明記する「クリア終端自体が失敗した場合の残余」の回帰）。
  (4) 即時再同期・クリア終端いずれも 1 回のみ実行され、再帰的リトライは
  行われないことを確認する。(5) 即時再同期・クリア終端対象でない他の
  フィールド・他のキーへその実行が波及しない（対象フィールド 1 件に
  閉じる）ことを確認する。
- **hydrate ドリフト属性の扱い（finding 3 対応、undo ではなく新規生成で
  解消することの確認）**: モックのライブ属性初期状態へ、達成 Node
  キャッシュ（`old_attrs`/`new_attrs` いずれにも）現れない属性を 1 件
  仕込む（SSR hydrate 由来のライブ専用属性を模す）。(1) 順方向
  `sync_attrs` でこの属性が削除されること（既存契約の再確認）、
  (2) このスコープが（`sync_attrs` の不一致等により）段 2 へ進んだ
  場合、段 2 で生成される新しい Element にはこのドリフト属性が一切
  含まれず、`new_attrs` 通りの属性集合のみを持つこと（「復元」を試みない
  ため、ドリフト属性の残存懸念自体が発生しないことの確認）。
- **XSS 回帰**: 既存の keyed list XSS 回帰テスト（SSR/SSG/CSR/WASM 各
  経路、`crates/wasm-client/tests/` 配下）を削除・弱体化しない。属性
  差分適用が新規属性検証迂回経路を作らないことを、既存の URL スキーム/
  `srcset`/イベントハンドラ属性ブロックのテストケースを流用して確認する。
  加えて、6.1「本書が保証する事項」1 の主張（段 1 の途中失敗による中間
  状態でも未検証値が観測されない）を、段 1 (B) 失敗直前までに成功した
  属性値がすべて `sync_attrs` の検証を通過済みであることの回帰として
  固定する。
- **cache-miss フォールバックの回帰**: プレースホルダ旧 `Node` が渡される
  経路で per-child diff がスキップされ、必ず従来の全再構築経路を通る
  ことを固定するテストを追加する（§5 不変条件の回帰防止）。加えて
  （本改訂で追加、PR #1395 codex-review 13 巡目 P0 対応）、cache-miss
  経路で `replace_item_children` が失敗し `ApplyOutcome::stale_update_keys`
  が非空になるケースを固定し、`apply_keyed_list_core`（既存の #1340
  fail-closed 防御）が達成 Node の合成を行わず
  `KeyedListApplyResult::ResyncRequired` を返すこと（`stale_update_keys`
  のまま終端しないこと）を確認する既存の回帰保証（`crates/wasm-client/src/keyed_dom.rs`
  の既存テスト）を、本書のスコープ外として削除・弱体化しないことを
  明記する。この `ResyncRequired` は本書 §6.1・§6.2 が定める即時再同期・
  クリア終端の対象になる（下記「段 3 到達後の即時再同期とクリア終端」参照）。
- **ネストした binding キャッシュ無効化の回帰（§6.3 の P1 契約固定）**:
  (1) 段 1 (A) narrow fallback が成功したスコープ配下にネストした
  `data-bind-list` がある場合、その field が `invalidated_nested_fields`
  へ追加されること、(2) narrow fallback しなかった、または別個に
  narrow fallback した兄弟スコープ配下の nested field はこの追加に
  含まれないこと（無効化範囲が narrow fallback したスコープ自身に
  閉じること）、(3) `set_text_data`／属性差分適用のみが起きた（narrow
  fallback に至らなかった）ケースでは `invalidated_nested_fields` への
  追加が発生しないこと、(4) 段 2（item 全置換）が成功した場合は item
  全体の nested field が追加されること、(5) 段 3（`resync_required`）
  経路では当該アイテム配下の nested field がアイテム単位で保守的に
  無効化されること。(6)（本改訂で追加、PR #1395 codex-review 10 巡目
  P1 対応）子孫（非ルート）Element が `data-bind-list` を持つ（ネスト
  binding のルートである）ケースで、その Element 自身の属性が段 1 で
  差分適用される（他の属性が変更されるが `data-bind-list` の値自体は
  新旧で同一）とき、`sync_attrs` へ渡す `reserved_attr` が
  `data-bind-list` であること（`data-key` と同じ予約属性フィルタ・
  再付加パスを通ること）をモックの呼び出し引数から確認し、`data-bind-list`
  の値が変更・削除されず（比較・書き換え対象から除外され）、ノードも
  再生成されないためこの単位単独では `invalidated_nested_fields` へ
  何も追加されないことを固定する（§6.3 の P1 契約固定）。(7)（本改訂で
  追加、PR #1395 codex-review 11 巡目 Bugbot Medium 対応）子孫（非
  ルート）Element が `data-bind-list` を持ち、旧新でその**値が異なる**
  （旧 `groupA`・新 `groupB` 等）ケースで、(a) `sync_attrs` は呼ばれず
  `reserved_attr` 保護も適用されず、このスコープが直ちに (A) 前提不一致
  として narrow fallback（`replace_item_children`）へ切り替わること、
  (b) narrow fallback が成功した場合、`invalidated_nested_fields` に
  **新旧両方の field 名**（`groupA` と `groupB`）が含まれること（新
  field は narrow fallback 後の新しい部分木の走査から、旧 field は
  §6.3 が定める明示的な追加規則から、それぞれ独立に加わることを確認
  する）、(c) narrow fallback 自体が失敗した場合は §6.2 のとおりアイテム
  全体が段 2 へ進み、§6.3 規則 3（段 2 成功時は item 全体の nested
  field を追加）が適用され、この場合も新旧両 field を含む item 全体の
  再収集で結果的に両方が捕捉されることを確認する。
