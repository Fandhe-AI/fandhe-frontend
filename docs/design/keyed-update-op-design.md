# 同一キー内容差分の diff 意味論・API 設計（イシュー #1322）

## 1. 目的とトレーサビリティ

- 本書はベンチ起点トラッキング #1313 → Phase 2 #1315（`keyed_dom` の CSR
  適用性能改善）→ #1321（keyed diff への Update op 導入）の第 1 弾（設計）
  として、#1321 の設計成果物を確定する。後続実装は #1323（`core` への
  `KeyedOp::Update` / 内容比較付き diff 関数の追加）・#1324
  （`wasm-client` の DOM 適用経路への反映と browser テスト）が担う。
- 解決する課題: 現行の `apply_keyed_list`
  （`crates/wasm-client/src/keyed_dom.rs`）はキー列の Insert / Remove /
  Move のみを diff し、**同一キーで内容（テキスト等）だけが変わった更新は
  no-op になる**。このため #1315 のベンチ実装ではプリミティブ直接操作で
  更新を書かざるを得ず、宣言的な keyed list 更新経路に API ギャップが
  存在する。
- 本書は **設計のみ**を成果物とし、コード変更を含まない。REQ-1（既定
  エスケープ）・REQ-11（性能）・`docs/design/dom-binding-update-design.md`
  （以下「更新設計書」）の既存確定設計との整合を保ったまま、#1323・
  #1324 が実装できる粒度まで API 形状・意味論を確定する。

## 2. 現状整理

- `crates/core/src/keyed.rs`: `keyed_list()` 構築 API
  （`data-bind-list` / `data-key` マーカー、構築時 fail-closed 検証）。
  diff 機能は持たない。`Node`（`crates/core/src/lib.rs`）は
  `#[derive(Debug, Clone, PartialEq, Eq)]` 済みであり、部分木同士の
  内容同値比較は外部依存を追加せず `core` 内で完結できる。
- `crates/wasm-client/src/keyed_diff.rs`: 純粋 diff 層。
  `KeyedOp { Remove, Insert, Move }` と `diff_keys(old_keys, new_keys)`
  （キー列の `&str`/`String` 比較のみによる O(n) 2 パス、DOM 非依存で
  native テスト可能）。`pub mod keyed_diff` として公開されている。
- `crates/wasm-client/src/keyed_dom.rs`:
  `apply_keyed_list(document, list_element, new_list_node)` が wasm32
  配線層を担う。**旧キー列を DOM（`data-key` 属性）から読み出して**
  `diff_keys` へ渡し、結果の `KeyedOp` 列を適用する。innerHTML 不使用・
  `RawHtml` fail-closed・URL スキーム / `srcset` / イベントハンドラ属性
  検証・SVG 名前空間対応を備える。
- `crates/wasm-full/src/lib.rs::apply_update_for_dirty`: dirty field
  ごとに `find_list_element` → `apply_keyed_list` を呼ぶ更新駆動。
  構造変化時に束縛点対応表（BindingTable）を再スキャンする。
- 既存確定設計: 更新設計書 §5（keyed list が構造変化を表現できる唯一の
  経路）・§7（仮想 DOM・汎用 diff 非採用の根拠）・§9（セキュリティ
  不変条件）。`docs/policy/intentional-non-adoption.md` §3.1（仮想 DOM、
  評価軸 4 点・再評価トリガー）。
- Phase 2（#1315）の安全設計不変条件: innerHTML 不使用・既存 DOM ノードを
  再生成しない・フォーカス保持。#1315 が対象としていたのは Insert /
  Remove / Move（構造変化）のみであり、この 3 op について本書は不変条件を
  一切緩めない（更新設計書 §5.3 が「本節の Insert / Remove / Move の
  意味論・キー照合方式は同文書でも不変のまま継承される」と明記する範囲と
  一致する）。本書が新設する `Update`（内容変更）は #1315 が定義していな
  かった新規操作であり、その適用範囲（アイテムルート要素の同一性は保持
  するが、内容が変わった子ノード列については子孫の DOM ノード同一性・
  内部フォーカスまでは保持しない）は §3.2・§3.3 で正式に確定する（イシュー
  #1330 レビュー指摘 P0 を受けた再確定。旧稿は「継承し緩めない」を `Update`
  にも及ぶ形で読める記述だったが、これは #1315 が定義していない範囲への
  過大な主張であり、§3.2/§3.3 の実際の挙動と矛盾していたため訂正する）。
- crate バージョン（本書執筆時点）: `fandhe-frontend-core` 0.2.0 /
  `fandhe-frontend-wasm-client` 0.3.0 / `fandhe-frontend-wasm-full` 0.7.1。

## 3. diff 意味論

### 3.1 変更検出

キーが新旧両列に存在し、かつ旧アイテムの `Node` と新アイテムの `Node` が
`PartialEq`（部分木全体の構造的同値比較）で不一致のときにのみ
`KeyedOp::Update` を発行する。変更がないキーは op を一切発行しない
（#1323 受入条件「余分な op を発行しない」に対応）。本設計は差分位置の
再帰的な特定（アイテム内部のどのノードが変わったかのパッチ生成）は
行わない ── アイテム単位で「変更あり／なし」の二値判定のみを行う
（詳細は §3.2 c 案）。

### 3.2 適用意味論（採用案・却下案）

採用案は「実装単純性」と「既存不変条件（アイテムルート要素自体の DOM
ノード再生成禁止）との両立」の 2 点で選定する。ルート要素配下の子孫の
フォーカス保持については本表の各案の判定に含めず、§3.3 で及ぶ範囲を
別途正式に確定する。

| 案 | 内容 | 判定 |
|----|------|------|
| a. アイテム全置換 | 変更検出したアイテムを `Remove` + `Insert` 相当で丸ごと作り直す | **却下**。アイテム**ルート要素自体**を破棄・再生成するため、ルート要素の DOM ノード同一性・イベント配線・アイテム間の並び安定性が失われる（更新設計書 §7.2、#1315/#1321 受入条件）。アイテムがフォーカスされている場合は当然フォーカス・入力途中の値・IME 変換状態も失われるが、却下の本質的な理由はルート要素の同一性喪失そのものであり、フォーカス喪失はその帰結の一つに過ぎない |
| b. テキストのみ更新 | アイテムルート要素は保持し、テキストノードの差し替えのみ行う | **却下（限定案として記録）**。`class` / `disabled` 等の属性変更に更新経路がなく、解決したい API ギャップ（「内容変更全般が no-op になる」）が部分的に残存する |
| c. **浅い in-place 更新（深さ 1 打ち切り）** | アイテムルート要素の同一性（DOM ノード参照）を維持したまま、(1) 子ノード列は新旧で不一致なら detached コンテナ上で `build_dom_node` 相当のプログラム的構築を先に行い構築成功を確認し、(2) 構築成功後、旧属性値・旧子ノードを保存したうえでライブ root 要素へ属性差分の適用と子ノード交換をコミットし、コミット中に失敗した場合は保存済みの旧値・旧子ノードへロールバックする | **採用**。a 案と異なり**ルート要素自体は再生成しない**ため、アイテム外からのフォーカスの戻り先・イベント配線・並び安定性は保持される。子ノード列が実際に変わる場合は子孫の DOM ノード同一性までは保持しない（この境界は a 案の却下理由とは独立した、意図的かつ文書化された制約であり、§3.3 で正式に確定する） |
| d. ノード全体の再帰 diff | アイテム内部の任意深さのノードを新旧比較し、変更箇所だけへ最小パッチを当てる（morphdom 型） | **却下**。仮想 DOM・汎用 diff 相当であり、§4 の評価軸に基づき非採用（`docs/policy/intentional-non-adoption.md` §3.1 と同じ判断軸） |

c 案の詳細:

- **ルート属性の差分適用（旧値の保存とコミット失敗時ロールバック、イシュー
  #1330 レビュー指摘 P0〔2 巡目〕を受けて再確定）**: 旧ノードの属性集合と
  新ノードの属性集合を比較し、削除属性・追加変更属性からなる操作列
  （`removeAttribute` / `setAttribute` の呼び出し列）を算出する。`data-key`
  / `data-bind-list`（更新設計書 §5.1 の予約属性）は比較・書き換えの対象外
  とする（§5 不変条件 3 参照）。属性値の検証規則（URL スキーム・
  `srcset` 候補分割・イベントハンドラ属性のブロック）は既存の
  `build_dom_node`（`crates/wasm-client/src/keyed_dom.rs`）が新規ノード
  構築時に適用する規則と同一のものを、Update 経路の属性適用にもそのまま
  適用する（検証規則を複製せず共有する）。属性名・属性値は Rust 側で
  この検証規則を通過した文字列のみが `setAttribute`/`removeAttribute` へ
  渡るため、無効な属性名・値そのものを原因とする失敗は事前に除外済みで
  ある。それでも `setAttribute`/`removeAttribute` が失敗しうる残りの経路
  （接続状態依存の挙動を持つカスタム要素の `attributeChangedCallback` が
  例外を送出する等、要素が実際にライブ DOM へ接続されているときにのみ
  発生しうる副作用）は、**detached な複製要素での事前検証では再現できな
  い**（複製要素は disconnected のため、"connected" 前提の reaction 経路
  を通らない可能性がある。旧稿の「複製での適用成功はライブ root 要素へ
  同一操作列を適用した場合の成功を保証する」という記述はこの点で誤りで
  あり撤回する）。このため事前検証には依存せず、代わりに**旧値の保存と
  失敗時ロールバック**でコミットフェーズの原子性を保証する:
  1. 適用対象となる属性名の集合（削除対象・追加対象・変更対象の和集合）
     について、ライブ root 要素の現在値を `getAttribute` で読み取り保存
     する（属性が存在しない場合は「不在」を表す sentinel を保存する）。
     この読み取りは副作用を持たず、値の観測のみである。
  2. 算出済みの操作列を新旧の並び順でライブ root 要素へ 1 件ずつ適用する。
  3. k 件目の操作が失敗した場合、直ちに適用を中断し、**既に成功した
     0..k-1 件目の操作を逆順にロールバックする**（保存しておいた旧値
     （sentinel の場合は `removeAttribute`、値がある場合は `setAttribute`
     でその値へ戻す）ことで、ライブ root 要素の属性を Update 適用開始前
     の状態へ復元する）。ロールバック自体も同じ `setAttribute`/
     `removeAttribute` を使うため理論上失敗しうる残余リスクが存在する
     （残余リスク発生時の扱い・ログ出力契約は §6 不変条件 6 が定義し、
     本節では二重に定義しない）。
- **子ノード列の再構築（detached 構築 → 検証 → 旧ノード保持 → 交換、
  イシュー #1330 レビュー指摘 P0〔2 巡目〕を受けて再確定）**: 子ノード列
  （テキスト・要素混在を含む）が新旧で一致しない場合、**新しい子ノード列
  を DOM 未接続（detached）のコンテナ（例: `DocumentFragment` または未接続
  の一時要素）上へ `build_dom_node` によるプログラム的構築（`create_element`
  → `set_attribute` → `set_text_content` → `append_child`）で組み立てる**。
  この構築は既存 DOM に一切触れずに行う。`build_dom_node` は子孫に
  `RawHtml` が含まれる場合や要素生成・属性設定に失敗した場合に `None` を
  返しうる（更新設計書 §5.2・§9）ため、構築フェーズで `None` が 1 件でも
  発生した場合は直ちに構築を中断し、detached コンテナごと破棄する。
  既存の子ノード列・ルート属性のいずれにも変更を加えず、当該アイテムの
  Update 適用全体（属性差分適用を含む）を諦めて他アイテムへの適用へ進む
  （§6 不変条件 6 の fail-closed 契約。旧 DOM 削除を構築成功の確認より
  先に行わない）。
  **子ノード列の detached 構築とルート属性差分の算出（上記）が両方とも
  成功した場合にのみ**、ライブ DOM への変更（コミットフェーズ）へ進む。
  コミットフェーズは次の順で行う:
  1. 上記のロールバック手順つき属性適用を実行する。属性適用自体が
     ロールバックしてもなお失敗する場合は、子ノードには一切触れず
     （旧子ノード列は無傷のまま）Update 適用全体を諦める。
  2. 属性適用が完了（成功またはロールバックにより元の状態へ復元）した後
     にのみ子ノード列を交換する。旧子ノードは削除と同時に破棄せず、
     `remove_child` の戻り値としてノード参照を**順序を保ったまま**
     `Vec` へ保持してから detached コンテナの新しい子ノード列を
     `append_child` で追加する。旧子ノードの取り外し（`remove_child`）・
     新子ノードの取り付け（`append_child`）はいずれも `web_sys` 呼び出しで
     あり理論上失敗しうるため、両フェーズを対称に扱う（イシュー #1330
     レビュー指摘 P0〔4 巡目〕を受けて明記。旧稿は `append_child` 失敗時の
     復元しか定義しておらず、`remove_child` 自体の失敗パスが未定義だった）:
     - **取り外しフェーズでの失敗**: `remove_child` が i 件目
       （`i < 旧子ノード件数`）で失敗した場合、直ちに取り外しを中断し、
       (a) 既に取り外し済みの旧子ノード 0..i-1 件を**元の順序で**
       `append_child` によりルート要素へ再度取り付け（i 件目以降は
       ルート要素にまだ residing しているため追加操作は不要）、
       (b) 直前に成功していた属性適用もロールバックしてルート要素全体を
       Update 適用開始前の状態へ復元する。新子ノード列（detached コンテナ
       上）には一切触れない（構築のみ済みで未使用のまま破棄する）。
     - **取り付けフェーズでの失敗**: 旧子ノードの取り外しがすべて成功した
       後、`append_child` が j 件目で失敗した場合は直ちに中断し、
       (a) 既に追加済みの新子ノード 0..j-1 件をルート要素から取り除き、
       (b) 保持しておいた旧子ノード列を**元の順序で** `append_child`
       により再度取り付け、(c) 直前に成功していた属性適用もロールバック
       してルート要素全体を Update 適用開始前の状態へ復元する。
     - **復元操作自体の失敗**: 取り外しフェーズ・取り付けフェーズいずれの
       復元（再取り付け・属性ロールバック）も `web_sys` 呼び出しである以上
       理論上失敗しうる残余リスクを持つ。この残余リスクの扱い（固定英語
       文言の警告ログを出し当該アイテム 1 件に閉じた不定状態を許容する）
       は §6 不変条件 6 が定義し、本節では二重に定義しない。
  「削除してから構築」ではなく「構築・検証してから、旧ノードを保持した
  まま交換し、失敗時は保持しておいた旧ノードで復元する」の順序を常に
  守る（detached 構築の事前検証に「ライブ DOM 操作は失敗しない」という
  過大な保証を持たせず、実際にライブ DOM 操作が失敗した場合の復元手段を
  設計に内蔵する）。テキストのみの変更（例: `<span>1</span>` →
  `<span>2</span>`）は、この手順でも結果として `set_text_content` 相当の
  1 回の DOM 操作に帰着する。子要素の内部に HTML パーサを一切経由しない
  （更新設計書 §9 不変条件 1 の延長）。
- **打ち切りの意味**: 「深さ 1」とはアイテムルート要素の属性は差分適用、
  子孫は変更があれば丸ごと再構築するという意味であり、子孫のさらに内側
  だけを選択的に更新する再帰比較は行わない。これにより diff 実装は
  「ルート属性比較 1 回 + 子ノード列同値判定 1 回」に収まり、コード量・
  レビューコストを小さく保つ。

### 3.3 制約（フォーカス保持の範囲、正式な受入基準の再確定）

本節は「本設計のスコープ外」として回避するものではなく、§3.2 c 案の
フォーカス保持契約の**及ぶ範囲を正式に確定する**節である（イシュー #1330
レビュー指摘 P0〔2 巡目〕を受けた再確定）。

- #1315 が定めた「既存 DOM ノードを再生成しない・フォーカス保持」は
  Insert / Remove / Move（構造変化）の文脈で定義された不変条件であり、
  更新設計書 §5.3 もこの 3 op の意味論のみを不変として継承すると明記する
  （§2 参照）。c 案はこの不変条件を Update 操作へ次の形で適用する:
  **アイテムルート要素自体は a 案（アイテム全置換）と異なり再生成しない**
  ため、Move 単体・Move と Update の併発いずれの場合も、アイテム外部から
  見たアイテムの同一性（並び位置・イベント配線・アイテム外からアイテムへ
  戻るフォーカスの戻り先）は #1315 の不変条件どおり保持される。
- 一方、変更されたアイテムの**内部**にフォーカスがある場合、子ノード列が
  実際に不一致（再構築対象）であれば内部フォーカス・キャレット位置・IME
  変換状態は保持されない。これは #1315 の不変条件を緩めたものではなく、
  #1315 が定義していなかった新しい操作（内容変更）に対して本書が新たに
  定義する境界である。編集中の入力値等、フォーカス・キャレット位置の
  保持が必須なノードについては、`data-bind-text` / `data-bind-attr`
  （更新設計書 §3・§4、既存の束縛点更新経路）を使う指針を実装ガイドとして
  #1323／#1324 に引き継ぐ（これらの経路は対象ノードを再生成せず値のみを
  更新するため、本書が新設する keyed list Update op とは独立にフォーカスを
  保持できる）。keyed list の Update op はアイテム単位の粗粒度な内容差分に
  向いた経路であり、フォーカス保持が必須な特定ノードの更新には向かない、
  という役割分担を本設計の受入基準として明記する。
- ネストした `keyed_list` を含むアイテム（アイテム内部に別の `keyed_list`
  呼び出しがある場合）は、外側の keyed list の Update 判定において内側
  keyed list 部分木も含めて `Node` の構造的同値比較に含まれる。すなわち
  内側リストの内容が変われば外側アイテムも「変更あり」と判定され、子ノード
  列再構築（内側リストの DOM ノードも再生成）が起きる。内側 keyed list を
  外側の Update 判定から独立させ、内側リスト自体の diff 結果を再利用する
  最適化は本書のスコープ外とする（内側リストが独立した dirty field として
  駆動される既存の `apply_update_for_dirty` 前提とは別に、外側アイテムの
  Update が発生した場合の扱いを明確化するに留める）。

### 3.4 op 発行順・既存互換

- 既存 3 op（`Insert` / `Remove` / `Move`）の発行順・内容は不変とする
  （#1323 受入条件「既存テスト無変更」）。`diff_keys`
  （キー列のみを見る既存関数）のシグネチャ・挙動・テストは変更しない。
- `Update` の発行位置は、既存の 2 パス（Remove パス → Insert/Move パス）
  の**後**に第 3 パスとして追加する: 2 パス終了後の「新しい並び」に
  対して、新旧両方のキー列に存在する保持キー（`Remove` パスで削除されな
  かったキー）**すべて**について、当該キーに対し第 2 パスで `Move` が
  発行されたか否かに関わらず、対応する旧アイテム `Node` と新アイテム
  `Node` を比較し、不一致であれば `KeyedOp::Update` を発行する（イシュー
  #1330 レビュー指摘 P1 を受けて確定。「位置が変わらないキーのみ」への
  限定は行わない）。発行順序はキーの新しい並び順（`new_keys` の順序）に
  固定する。判定条件は「保持キーであるか」の一意な条件のみであり、
  実装解釈の余地を残さない。
- `Move` されたアイテムについても内容変更が同時に起きうる（キーは同じだが
  位置も内容も変わるケース）。この場合は上記の通り `Move` 発行に加えて
  同一キーへの `Update` も発行する（1 キーに対し `Move` と `Update` の
  両方が起きうることを許容する。位置決定と内容適用は独立した関心であり、
  `Move` 1 種類に内容更新の意味を混在させない）。op 列全体における
  順序は、`Move` は第 2 パス（`new_keys` 順）で先に発行され、`Update` は
  第 3 パス（`new_keys` 順）で後に発行されるため、**同一キーの `Move` と
  `Update` は隣接しない**（両パスの間に他キーの `Move`/`Insert` op が
  挟まりうる）。具体例: `old_keys = ["a", "b"]`・`new_keys = ["b", "a"]`
  で、`a` は位置のみ変更（内容一致）、`b` は位置と内容の両方が変更された
  場合、期待される op 列は `[Move{key: "b", ...}, Update{key: "b"}]`
  （`a` は Move も Update も発行しない。新しい並び順が `["b", "a"]`
  のため `b` が先に処理される）。`old_keys = ["a", "b"]`・
  `new_keys = ["a", "b"]`（Move 対象なし）で両キーとも内容変更がある
  場合は `[Update{key: "a"}, Update{key: "b"}]`（`new_keys` 順）となる。

### 3.5 計算量・SSR/SSG への影響

- キー照合は既存どおり O(n)（`old_keys.len() + new_keys.len()`）。内容比較
  パスは保持キー（Remove されなかったキー）それぞれについて対応する新旧
  `Node` 部分木の `PartialEq` 判定を行うため、計算量は
  O(Σ 保持キーの部分木サイズ) が追加される。全体としてリストサイズに線形の
  計算量に留まり、既存の「仮想 DOM を導入しない」判断（更新設計書 §7.1）の
  前提（変更フィールド数に比例する計算量）を破らない。
- `render()`（SSR/SSG/CSR 初回マウント共通のレンダラ）の出力・シグネチャは
  一切変更しない。本設計は CSR 側の差分適用（`wasm-client`）にのみ関わる。

## 4. API 形

### 4.1 責務分担（受入条件の中核）

- **op 生成（diff・内容比較）= `fandhe-frontend-core`**。DOM 非依存で
  `cargo test -p fandhe-frontend-core` の native 単体テストとして検証
  でき、`forbid(unsafe_code)`・外部依存ゼロの制約下に置く。
- **DOM 適用 = `fandhe-frontend-wasm-client`**。`web-sys` を用いた実 DOM
  操作（要素生成・属性適用・`insert_before`・削除）に閉じる。browser
  テスト（`wasm-pack test --headless`）で検証する。

### 4.2 採用案: 明示 API + core への diff 移管

- **core（`crates/core/src/keyed.rs` へ追加）**:
  - `KeyedOp`（`Remove` / `Insert` / `Move` / **`Update`**）を core 側で
    新設する。既存 3 variant は wasm-client 側 `KeyedOp` と等価な情報を
    持つ（`Update` variant のみ新規: `key: String` と、適用に必要な新旧
    `Node` 参照または複製済み `Node` を持つ。具体的なフィールド型・
    所有権設計（`&Node` 借用か `Node` 複製か）は #1323 側の実装確定事項
    とする）。
  - `diff_keys(old_keys: &[String], new_keys: &[String]) -> Vec<KeyedOp>`
    （キー列のみを見る既存互換版）を core へ移設する。
  - 内容比較付きの新設 diff 関数（例: `diff_keyed_items(old_items:
    &[(String, Node)], new_items: &[(String, Node)]) -> Vec<KeyedOp>`。
    正式名称は #1323 で確定）を追加し、§3 の意味論（3 パス: Remove →
    Insert/Move → Update）を実装する。
- **wasm-client（`crates/wasm-client/src/keyed_diff.rs`）**: 型定義・
  `diff_keys` の実体を core からの re-export へ置き換える
  （`pub use fandhe_frontend_core::keyed::{KeyedOp, diff_keys};` 相当）。
  型の同一性を保つことで既存の呼び出し側コンパイル互換を維持する。
- **wasm-client（`crates/wasm-client/src/keyed_dom.rs`）**: 既存の
  `apply_keyed_list(document, list_element, new_list_node)` のシグネチャ・
  挙動は**不変**とする（DOM 上の `data-key` 列からしか旧内容を得られない
  ため、引き続き `Update` は発行されない）。`Update` に対応する新規関数
  （例: `apply_keyed_list_with_previous(document, list_element,
  previous_list_node, new_list_node)`。正式名称は #1324 で確定）を追加し、
  呼び出し側が直近の `Node`（前回描画時の keyed list ノード）を保持して
  いる場合にのみ内容比較付き diff を使う。この新規関数は `new_list_node`
  をそのまま返さず、**実際に DOM へ反映された結果を表す値**（以下
  「達成 Node」。形式は #1324 で確定するが、少なくとも (a) 全アイテムが
  意図どおり適用された「達成 `Node`」と (b) 一部アイテムが §6 不変条件 6
  の残余リスク（ロールバック自体の失敗）により不定状態になった「要再同期」
  信号の 2 種類を区別可能な戻り値とする）を返す。理由・呼び出し側の扱いは
  §4.2a で定める。
- **wasm-full（`crates/wasm-full/src/lib.rs`、#1324 で反映）**: `Runtime`
  は field ごとに `Node` を保持するが、**保持対象は呼び出し側が渡した
  `new_list_node`（意図した新しい内容）ではなく、新 API が返す「達成
  Node」のみ**とする（イシュー #1330 レビュー指摘 P1〔3 巡目〕を受けて
  再確定。旧稿はこの区別を欠いており、詳細は §4.2a）。保持がない初回描画・
  §4.2a の再同期契約が発動したフォールバック時は既存の `apply_keyed_list`
  （DOM 読み出し）経路を使う。

### 4.2a 保持 Node の更新規則（適用失敗時の再同期契約、イシュー #1330
レビュー指摘 P1〔3 巡目〕を受けて新設）

§4.2 の新 API が「達成 Node」ではなく呼び出し側の意図（`new_list_node`）を
そのまま `Runtime` の保持 `Node` へ書き戻すと、次の恒久劣化が起こりうる:
あるアイテムの Update・Insert・Move・Remove のいずれかが DOM 適用の途中で
失敗した場合、実 DOM は旧内容のまま（Update は §3.2/§6 不変条件 6 の
ロールバックにより旧状態へ復元、Insert は §6 不変条件 3 の fail-closed に
より当該アイテムがそもそも挿入されない等）だが、保持 `Node` だけが
「新しい意図」へ進んでしまう。次回同じ view（同一内容）が返された際、
保持 `Node` と新 `Node` が一致するため diff はゼロ件になり、失敗した
アイテムに対応する op が二度と発行されず、実 DOM だけが恒久的に取り残
される。以下でこれを防ぐ更新規則を定める。

- **達成 Node の定義（op 種別ごと）**: §4.2 の新 API が返す「達成 Node」は
  「呼び出し後に実 DOM が実際に表している内容」を表す `Node` である。
  - `Update`: アイテムごとに、§3.2/§6 不変条件 6 のコミットフェーズが
    完了した（成功またはロールバックにより元へ復元）場合は、当該アイテム
    について実際に DOM 上へ残った内容（成功なら新値、ロールバックなら
    旧値）を達成 Node へ採用する。ロールバック自体が失敗した場合（§6
    不変条件 6「残る有限のリスク」）は、当該アイテムの内容が新旧いずれと
    も一致しない不定状態であるため、「新値」「旧値」のどちらを記録しても
    虚偽の表明になる。この場合は達成 Node 全体ではなく**「要再同期」信号**
    を返し（§4.2 参照）、`Node` を一切合成しない。
  - `Insert`: `build_dom_node` が `None` を返し当該アイテムの挿入をスキップ
    した場合（更新設計書 §5.2・§9、既存 fail-closed 契約）、達成 Node は
    当該キーを**含まない**（実 DOM に存在しないアイテムをキャッシュ上だけ
    「挿入済み」として扱わない）。
  - `Remove` / `Move`: 現行 `apply_keyed_list` の適用対象であり、本書は
    これらの意味論・失敗経路を変更しない（§2・§3.4）。達成 Node は実行後の
    実 DOM 上のキー列・並び順をそのまま反映する。
- **`Runtime` 側の保持規則**: `Runtime` は新 API の戻り値が「達成 Node」で
  あった場合に限り、それを次回の保持 `Node` として書き換える。戻り値が
  「要再同期」信号であった場合、**保持 `Node` は書き換えず破棄する**
  （次回呼び出しは §4.2 で述べた「保持が破棄されたフォールバック」経路
  ＝既存の `apply_keyed_list`（DOM 読み出し）を使う）。
- **再同期時の収束契約**: 「要再同期」信号を受けて破棄した field は、次回
  以降 `apply_keyed_list` の DOM 読み出し経路（`data-key` 列比較のみ）へ
  フォールバックする。このフォールバックは**キー列の Insert/Remove/Move
  は正しく再同期できるが、同一キーのままの内容差分は検出できない**
  （`Update` は発行されない、§2）。したがって §6 不変条件 6 の残余リスク
  （ロールバック失敗）が発生したアイテムについては、フォールバック経路
  だけでは不定状態のまま収束が保証されない。この収束を保証するため、
  「要再同期」信号を発した対象キーについては、フォールバック直前に
  `wasm-client` 側で当該アイテムの DOM ノードを削除してから
  `apply_keyed_list` を呼ぶ（＝次回描画でキー列上「新規」として扱われ、
  `Insert` によって新しい内容で作り直される）。これにより、当該アイテム
  1 件はルート要素の同一性・内部フォーカスを犠牲にする代わりに、次回
  描画で必ず新しい意図どおりの内容へ収束することを保証する（ノード
  同一性を犠牲にする判断は、対象アイテムがそもそも新旧いずれとも
  一致しない不定状態にあり §3.3 が保証するフォーカス保持契約の対象外で
  あるため妥当である）。他アイテムへの `Update`/`Insert`/`Move`/`Remove`
  適用は §6 不変条件 6「1 アイテムの失敗が他アイテムを道連れにしない」の
  とおり妨げられない。

### 4.3 却下案: 暗黙差分（DOM からの旧内容読み出しで Update 判定）

`apply_keyed_list` が現行どおり DOM（`data-key` 属性・`textContent` 等）
から旧内容を読み出して `Update` 判定まで行う案は却下する。理由:

1. op 生成が wasm-client に残り、§4.1 の責務分担（op 生成は core）に
   反する。
2. DOM を真実源とする内容比較は、ブラウザの属性値正規化（例: 数値属性の
   表現ゆれ）・空白文字の扱いの影響を受け、決定性（更新設計書 §7.4「決定性」
   の評価軸）を損なう。
3. DOM 読み出しに依存する比較ロジックは native 単体テストで検証できず、
   `cargo test -p fandhe-frontend-wasm-client` のみでは browser テスト
   （実行コストの高い経路）を必ず経由する形になる。

### 4.4 後方互換（0.x マイナーの範囲）

- `KeyedOp` への `Update` variant 追加は、呼び出し側の非網羅
  （exhaustive でない）`match` を壊しうる破壊的変更である。イシュー #638
  規約（0.x の破壊的変更はマイナーバンプ）に従い、#1323 実装時に
  `fandhe-frontend-core` を 0.2.0 → 0.3.0 へ、#1324 実装時に
  `fandhe-frontend-wasm-client` を 0.3.0 → 0.4.0 へ、それぞれバンプする
  ことを実装手順として明記する。依存元クレート（`fandhe-frontend-wasm-full`
  等）の `version = "..."` 要求追随は `xtask check-dep-versions --fix`
  （`.claude/rules/ci.md` `dep-version-check` ジョブ参照）で機械的に行う。
- 既存の公開 API（`keyed_list()` / `apply_keyed_list()` /
  `diff_keys()` のシグネチャと挙動）は不変のまま維持する。破壊的変更は
  `KeyedOp` の variant 追加のみに閉じる。

## 5. 仮想 DOM との境界（`intentional-non-adoption.md` §3.1 評価軸での確認）

`docs/policy/intentional-non-adoption.md` §3.1 が定める 4 つの評価軸に
照らし、本設計が仮想 DOM・汎用 diff の再導入に該当しないことを確認する。

- **明示性**: 対象は `data-key` で特定された keyed list の直下アイテム
  1 件に閉じる。どのノードが Update 対象になりうるかは `grep -r
  'data-bind-list\|data-key'` で静的に把握できる既存の明示性を維持する。
  仮想 DOM のようにコンポーネントツリー全体が diff 対象になるわけではない。
- **決定性**: 判定は `Node` の構造的 `PartialEq`（値の同値性）のみに
  基づき、要素種別の推定・key のヒューリスティック推定を行わない。同じ
  新旧 `Node` 対に対して常に同じ op 列が決定的に得られる。
- **機械検証可能性**: §3 の op 発行規則（3 パス固定・発行順固定）は
  native 単体テストで op 列を決定的に固定できる（§7 テスト計画）。
- **コンテキスト消費**: 追加実装は「アイテムルート属性の差分適用 1 パス
  + 子ノード列同値判定 1 パス」に限定され、汎用 diff アルゴリズム
  （reconciliation）のような新規の大きな抽象層を追加しない。

**結論**: 本設計は「keyed list 専用経路の拡張（アイテム単位の浅い
in-place 更新）」であり、ノード木の任意位置を対象とする再帰 diff
（仮想 DOM・morphdom 型汎用 diff）は導入しない。`docs/policy/
intentional-non-adoption.md` §3.1 の再評価トリガー（perf-browser ゲート
での REQ-11 受け入れ基準の恒常的未達）には該当しない。

## 6. セキュリティ不変条件（更新設計書 §9 の継承）

Update 適用経路も更新設計書 §9 の既存不変条件をすべて継承し、緩めない。

1. **HTML 非解釈**: 子ノード列の再構築・テキスト差し替えは
   `set_text_content` / プログラム的な要素構築のみを経由し、
   `innerHTML` / `insertAdjacentHTML` を一切使わない（更新設計書 §9
   不変条件 1 の延長）。
2. **属性適用は `setAttribute`/`removeAttribute` のみ**: URL スキーム・
   `srcset` 候補分割・イベントハンドラ属性（`on*`）のブロックは、既存の
   `build_dom_node` が新規ノード構築時に適用する検証規則と同一のものを
   Update 経路の属性差分適用にも適用する（§3.2 c 案、規則の複製ではなく
   共有関数の再利用とする）。
3. **`RawHtml` は部分木ごと fail-closed**: keyed list アイテム内に
   `RawHtml` ノードが含まれる場合の扱いは既存の `keyed_list()` 構築時
   検証（`KeyedListError::NonElementItem` 等、更新設計書 §5.2）を継承し、
   Update 経路のために新たな迂回を作らない。
4. **予約属性は Update 対象外**: `data-key` / `data-bind-list`
   （更新設計書 §5.1）は §3.2 の属性差分適用の比較対象・書き換え対象から
   除外する。Update 経路がキー照合契約自体を書き換えられないことを構造的
   に保証する。
5. **`raw_html()` を呼ばない**: 束縛点更新・keyed list Insert/Remove/Move
   と同様、Update 経路にもエスケープ迂回オプトインを組み込まない（REQ-1）。
6. **fail-closed（属性適用・子ノード再構築いずれも部分適用を放置しない、
   イシュー #1330 レビュー指摘 P0〔2 巡目〕を受けて再確定）**: 構築フェーズ
   （detached コンテナ上での新子ノード列の構築・§3.2）で失敗が起きた場合は
   ライブ DOM に一切触れない（旧稿から不変）。これに加え、コミットフェーズ
   （ライブ root 要素への属性適用・子ノード交換）で失敗が起きた場合の契約
   を、**事前検証による「失敗しないことの保証」ではなく、旧値保存に基づく
   ロールバックによる「失敗しても元に戻ることの保証」**として定める（旧稿
   の「複製での事前検証によりライブ DOM 上で部分適用が構造的に発生しない」
   という記述は、接続状態に依存するカスタム要素の reaction 等 detached
   複製では再現できない失敗経路を見落としており撤回した）:
   - 属性適用（§3.2）が k 件目で失敗した場合、0..k-1 件目を逆順にロール
     バックし、ライブ root 要素の属性を Update 適用開始前の状態へ復元する。
     子ノードには一切触れていないため、復元後は「何も変更されなかった」
     状態と外形的に一致する。
   - 子ノード交換（§3.2）が旧子ノード i 件目の `remove_child` で失敗した
     場合、既に取り外し済みの旧子ノード 0..i-1 件を元の順序で再度取り
     付け、直前に成功していた属性適用もロールバックする（イシュー #1330
     レビュー指摘 P0〔4 巡目〕対応。取り外し途中の失敗を「後続の
     `append_child` が失敗した場合」の一種として扱わず、独立した失敗
     パスとして復元手順を定義する）。
   - 子ノード交換（§3.2）が旧子ノードの取り外しをすべて終えた後、新子
     ノード j 件目の `append_child` で失敗した場合、追加済み新子ノードを
     取り除き、保持しておいた旧子ノード列を元の順序で再度取り付け、
     直前に成功していた属性適用もロールバックする。
   - **残る有限のリスク**: ロールバック自体（`setAttribute` /
     `removeAttribute` / `append_child` の逆操作）が失敗する可能性は理論上
     排除できない（例: ロールバック実行中に要素が別の経路で DOM から
     切り離される等の外部要因）。ロールバックが失敗した場合に限り、当該
     アイテム 1 件のみ最終状態が Update 適用開始前・完了後のいずれとも
     異なる不定状態になりうることを、この残余リスクとして明示的に許容
     する（`unwrap()`/`panic!` は使わず、固定英語文言の警告ログ〔不変条件 7〕
     を出して処理を継続する）。この不定状態は当該アイテム 1 件に閉じ、
     他アイテムへの Update 適用には波及しない（更新設計書 §9 不変条件 6
     と同じ「1 アイテムの失敗が他アイテムを道連れにしない」設計）。
     ロールバック失敗自体は通常操作の失敗（属性名検証済み・detached 構築
     検証済みの経路）よりさらに稀な二重失敗であり、意図的に「完全な原子性
     の証明」ではなく「実行可能な範囲の最大努力の復元 + 残余リスクの明示」
     を受入基準とする。
7. **ログの機微情報非露出**: Update 適用時の警告ログは固定英語文言のみとし、
   キー値・アイテム内容（アプリ状態）を含めない（更新設計書 §9 不変条件 7
   の継承）。
8. **保持 `Node` は実 DOM と乖離しない（イシュー #1330 レビュー指摘 P1
   〔3 巡目〕を受けて新設）**: `Runtime`（wasm-full）が保持する keyed list
   の `Node` は、常に「実 DOM が実際に表している内容」（§4.2a の達成
   Node）でなければならない。呼び出し側が意図した新しい内容（診断結果
   `new_list_node`）をそのまま保持へ書き戻すことは、部分適用失敗
   （不変条件 6）と組み合わさると同一 view の再適用で診断が偽陰性
   （ゼロ件 diff）になり、実 DOM が恒久的に取り残される。§4.2a の保持
   規則・再同期契約（要再同期信号時は保持を破棄し、対象アイテムの DOM
   ノードを削除してから次回 `apply_keyed_list` の Insert 経路で作り直す）
   をこの不変条件の具体化として維持する。

## 7. テスト計画（#1323／#1324 受入基準へのマッピング）

- **core（#1323）**:
  - 同一キー内容変更のみ（構造変化なし）で `Update` 1 件のみが発行される
    ことを固定するテスト。
  - 内容変更なし（新旧 `Node` が完全一致）で op がゼロ件になることを固定
    するテスト。
  - `Insert` / `Remove` / `Move` との混在ケース（例: あるキーは削除、
    別キーは新規挿入、別キーは移動かつ内容変更）で、無関係キーへの
    余分な op が発行されないことを固定するテスト。
  - 既存の `diff_keys` テスト（`crates/wasm-client/src/keyed_diff.rs` の
    move 元テスト群）は core への移設後もすべて無変更で通過することを
    確認する。
- **wasm-client（#1324）**:
  - 同一キー・新テキスト内容での `set_text_content` 相当の DOM 更新を
    browser テストで確認する。
  - `<script>` タグ相当のペイロードを内容変更として渡した際に HTML として
    解釈されないことを確認する XSS 回帰テスト（既存の keyed_dom XSS
    回帰テストと同型）。
  - Update 対象アイテムのルート要素が `is_same_node` で同一 DOM ノードの
    まま保たれる（再生成されない）ことを確認するテスト。
  - Update 実測のオーバーヘッドが既存操作（#1315 実測 1.32ms 相当）の
    2 倍以内に収まることを確認する性能回帰テスト（perf-browser ハーネス
    経由）。
  - 属性適用が複数件（削除・追加・変更混在）となるケースで、途中の
    `setAttribute`/`removeAttribute` 呼び出し（k 件目、`k < n`）へ失敗を
    注入した場合、ロールバックによりライブ root 要素の属性が Update 適用
    開始前の値へ復元され（1 件も正味変更が残らず）、子ノードも一切変更
    されないことを確認するコミットフェーズ失敗注入テスト（§6 不変条件 6
    のロールバック契約の固定、イシュー #1330 レビュー指摘 P0〔2 巡目〕
    対応）。
  - 子ノード交換で旧子ノード i 件目（`i < 旧子ノード件数`）の
    `remove_child` へ失敗を注入した場合、既に取り外し済みの旧子ノードが
    元の順序でルート要素へ復元され、直前に成功していた属性適用も
    ロールバックされ、新子ノード列（detached コンテナ側）には一切
    触れられないことを確認するコミットフェーズ失敗注入テスト（§6 不変
    条件 6 のロールバック契約の固定、イシュー #1330 レビュー指摘 P0
    〔4 巡目〕対応）。
  - 子ノード交換で新子ノード j 件目（`j < 交換対象件数`）の `append_child`
    へ失敗を注入した場合、追加済み新子ノードが取り除かれ、保持していた
    旧子ノード列が元の順序で復元され、直前に成功していた属性適用も
    ロールバックされることを確認するコミットフェーズ失敗注入テスト
    （同上）。
  - 上記 2 件のいずれについても、対象アイテム以外のアイテムへの Update
    適用が妨げられないこと（§6 不変条件 6「1 アイテムの失敗が他アイテムを
    道連れにしない」）を、複数アイテムを含む keyed list で確認する。
  - **保持 Node の更新規則・再同期の収束（§4.2a・§6 不変条件 8、イシュー
    #1330 レビュー指摘 P1〔3 巡目〕対応）**:
    (a) コミットフェーズ失敗注入（属性適用または子ノード交換、ロール
    バック成功）により 1 アイテムの Update 適用が失敗（旧内容へ復元）した
    直後、`Runtime` 相当のハーネスが保持する `Node` を新 API の戻り値
    （達成 Node）で更新し、**同一の新 view を再度渡して 2 回目の適用を
    行う**。1 回目で保持 Node が呼び出し側の意図（失敗した新内容）へ
    誤って進んでいた場合は 2 回目の diff がゼロ件になり実 DOM が旧内容の
    まま取り残されるはずだが、達成 Node ベースの保持規則では 2 回目の diff
    でも同一キーへ `Update` が再発行され、失敗要因を除去した状態で
    2 回目の適用を行うと実 DOM が新内容へ収束することを確認する。
    (b) ロールバック自体の失敗を注入し（§6 不変条件 6「残る有限のリスク」）、
    新 API が「要再同期」信号を返すこと、ハーネスがこれを受けて当該
    field の保持 `Node` を破棄すること、その後の再描画で当該アイテムの
    DOM ノードが削除されたうえで `apply_keyed_list`（既存の Insert 経路）
    により新しい意図どおりの内容で作り直され、実 DOM が新内容へ収束する
    ことを確認する。
- **スコープ外**: #1319／#1320 の性能施策一般、`wasm-thin` への適用
  （`docs/policy/intentional-non-adoption.md` §3.10 の非採用判断を継承し
  対象外）、束縛点更新（`crates/wasm-client/src/binding.rs`）自体の変更。
