  うち、実行可能コード（`bin`/`main` 相当のエントリを持つ JS）を含まない

  ラッパーであり、本書はその**後段ゲート**として「取り込んだパッケージが

## 2. 判定対象と前提

- **判定対象**: `install.sh --dir <project-dir>` でインストールされた
  `<project-dir>/node_modules/` 配下の全パッケージ（scoped パッケージ
  `@scope/name` および transitive 依存を含む）。
- **実行タイミング**: インストール直後・生成物を配布物（`static/` 等）へ
  取り込む前。`install.sh` による `--ignore-scripts` 強制インストールの
  **後段ゲート**として位置づけ、両者は独立に迂回不能であることで多層防御
  を構成します（`install.sh` 単体では明示 `require()` は防げないため）。
- **前提契約**: 本検証はインストール経路が必ず `install.sh` 経由である
  ことを前提とします。`install.sh` を経由しない `node_modules` に対して
  実行しても構いませんが、その場合ライフサイクルスクリプトが実行済みの
  可能性がある点は本検証の範囲外です（`install.sh` の責務）。

## 3. 判定ルール（3 層検査）

判定は **denylist（既知の危険パターンを拒否）ではなく allowlist
（既知の安全パターンのみ許可・それ以外は既定拒否）** を基本方針とします。
根拠: 未知の実行形式（`.node`・`.wasm`・シェルスクリプト等）の取りこぼしを
構造的に防ぐためであり、`rws-core` の「既定エスケープ・明示オプトイン」と
同じ fail-safe 原則に従います。

### 3.1 Rule 1: `package.json` メタデータ検査

| 検査項目 | 判定 | 根拠 |
|---------|------|------|
| `bin` フィールドが存在（文字列・オブジェクトいずれも） | **違反** | REQ-12 受け入れ基準 2 の直接要求 |
| `main` / `module` / `browser` / `exports` が JS 実行エントリ（`.js`/`.mjs`/`.cjs`/`.node`）を指す | **違反** | 実行コードへの参照そのもの |
| `main` 等が非実行ファイル（例: `.css`）のみを指す | 許容 | CSS 配布パッケージの実在慣行を尊重（安全側判断だが過度な拒否は例外機構 §3.3 で救済する設計のため、ここは緩めてよい） |
| `main` 等のフィールドが欠落 | 違反としない | Rule 2 のファイル実体走査で担保するため、フィールド欠落のみを理由に拒否しない |
| `scripts` にライフサイクルスクリプト（`preinstall`/`install`/`postinstall`/`prepare` 等）が存在 | **違反** | `--ignore-scripts` で無効化済みだが、静的アセット限定パッケージとして本来不要であり、存在自体が「実行コードを想定したパッケージ」である兆候のため安全側で拒否する。過検知は例外機構で個別許可する |

### 3.2 Rule 2: ファイル実体の拡張子 allowlist 検査

パッケージ配下の全ファイルを走査し、**許可拡張子リストに一致しない
ファイルが 1 つでもあれば違反**とします。

**許可拡張子（初期案）**:

```
.css .woff .woff2 .ttf .otf .eot
.svg .png .jpg .jpeg .gif .webp .avif .ico
.json .md .txt
```

および拡張子なしファイルのうち `LICENSE` / `LICENSE-*` / `NOTICE` /
`README` / `README.*`（大文字小文字を区別しない前方一致）。

**明示的に拒否する境界ケース（判断根拠を明記）**:

| 拡張子・パターン | 判定 | 理由 |
|------|------|------|
| `.js` / `.mjs` / `.cjs` / `.node` / `.wasm`（`.min.js` を含む） | **拒否** | 実行可能コードそのもの。クライアント持ち込み JS は REQ-12 の除外事項 |
| `.sh` / `.py` / その他スクリプト言語拡張子 | **拒否** | 実行可能コード |
| `.d.ts`（TypeScript 型定義） | **拒否** | 実行コードではないが、本フレームワークは Rust 実装であり型定義の利用先がない。「使わないものは許可しない」という allowlist の既定拒否原則を優先する |
| `.map`（source map） | **拒否** | 対応する実行コード（JS）の存在を示唆し、静的アセット限定パッケージには本来不要 |
| `.scss` / `.less` | **拒否** | コンパイルにビルドプラグイン実行を要し、PoC-6 が「対象外」と結論づけた能動的コード実行の用途に接続するため |

### 3.3 Rule 3: ファイル属性・内容の追加検査

allowlist（Rule 2）を通過したファイルであっても、以下に該当すれば違反と
します（拡張子偽装・隠蔽への対策）。

- **shebang**: ファイル先頭が `#!` で始まる → **違反**。拡張子を偽装した
  実行スクリプトを検出するための保険。
- **実行ビット**: ファイルに実行パーミッション（`+x`）が立っている →
  **違反**。静的アセットに実行ビットは本来不要。
- **`.svg` 内のスクリプト混入**: `.svg` は許可拡張子だが、
  `<script` 要素または `on*` イベント属性（`onload=` 等）を含む場合は
  **違反**。SVG 経由のスクリプト混入・XSS 面（REQ-1 の既定エスケープ方針
  との整合）への防御であり、単純な文字列検査で安全側に倒します
  （正規表現による大雑把な一致で過検知を許容し、見逃しを避ける）。

## 3.4 例外・オプトイン機構

過検知（実在の静的アセットパッケージが誤って弾かれる）の救済として、
プロジェクト側の明示許可ファイル（例:
`tools/npm-asset-build/allowlist.toml`）で「パッケージ名 + 該当ルール ID +
理由」を単位に個別免除できる設計とします。

- `raw_html()` と同様に**明示オプトイン**の設計とし、パッケージ名の
  ワイルドカード指定・ルール全体の無効化（例: 「Rule 2 を全パッケージで
  無効化」）は設けません。免除は 1 パッケージ・1 ルール単位の宣言のみを
  許可します。
- 免除エントリには理由（自由記述）を必須項目とし、レビューで免除の妥当性
  を判断できるようにします。
- 例外機構のファイルフォーマット・パーサ実装は TASK-12.2b（#123）の
  スコープです。本書ではフォーマット方針と制約のみを確定します。

## 4. 実装インターフェース契約（#123 への引き渡し）

- **CLI**: `check_static_only.py --node-modules <path>`
  （エイリアスとして `--dir <project-dir>` から `<project-dir>/node_modules`
  を導出する形も許容してよい）。
- **終了コード**: `0` = 全パッケージ合格 / `1` = 違反あり / `2` = 実行
  エラー（パス不在等）。
- **出力形式**: 違反ごとに「パッケージ名 / ルール ID / 該当ファイルパス /
  理由」を 1 行で列挙する（CI ログで判読可能な形式。例:
  `VIOLATION package=foo rule=R1-bin file=package.json reason="bin field present"`）。
- **実装制約**: Python 3 標準ライブラリのみを使用する。pip 依存の追加は
  検証ツール自身のサプライチェーン面を拡大するため不可とします
  （依存クレート追加がユーザー承認必須であるのと同じ考え方を踏襲）。
- **symlink・パストラバーサル対策**: `node_modules` 配下の走査時に
  symlink を辿らない（symlink エントリはそれ自体を違反として扱うか、
  少なくとも走査対象から除外し警告を出す）。`node_modules` の外側へ
  出るパス（`..` を含む解決結果等）は走査対象に含めない。
- **テスト設計方針**: `test_install.sh`（TASK-12.1a の先例）に倣い、
  fixture パッケージ（合格 / `bin` あり / `.js` 混入 / shebang 混入 /
  実行ビット付きファイル / SVG 内 script 混入 / 例外許可済み）による
  オフラインテストを `tools/npm-asset-build/tests/` に配置する。

## 5. スコープ外の明記

- **CI ワークフローへの組み込み**: TASK-12.2c（#124）のスコープです。
  現行 `.github/workflows/ci.yml` は本書執筆時点で
  `tools/npm-asset-build/` のテストを実行していません。
- **配布バイナリ・ブラウザ配信物側の NPM 非混入検証**: TASK-12.3（#125）
  のスコープです。
- **過大な安全性主張の禁止**: 本検証はビルド時に取り込む静的アセットの
  実行コード非混入を機械的に検証するものであり、PoC-6 が指摘した
  「ビルド時のリスク（`build.rs`・手続きマクロ等、Cargo エコシステム
  全体の構造的リスク）」自体を解消するものではありません。本書・実装は
  この限界を明示し、「NPM パッケージを取り込んでも完全に安全」という
  一般化した主張は行いません。

## 6. セキュリティ考慮事項（OWASP Top 10 観点）

- **A03 インジェクション / XSS**: SVG 内 `<script>` 要素・イベント属性の
  検査（Rule 3）により、静的アセット経由のスクリプト混入経路を塞ぎます。
  既定エスケープ（REQ-1）を弱める記述は本書に含めていません。
- **A05 セキュリティ設定ミス**: 判定を denylist ではなく allowlist
  （既定拒否・fail-closed）で設計し、未知の実行形式の取りこぼしを
  構造的に防ぎます。例外機構は 1 パッケージ・1 ルール単位の明示オプトイン
  に限定し、ワイルドカード許可・ルール全体の無効化を禁止します。
- **A06 脆弱な依存 / A08 サプライチェーン**: 本タスク自体が REQ-12 の
  サプライチェーン対策（PoC-2 脅威モデル面 (b)）の中核です。
  `check_static_only.py` を Python 標準ライブラリのみで実装する制約を
  課し、検証ツール自身が新たな依存面を持ち込まないようにします。
  `--ignore-scripts` の限界（明示実行までは防げない）を本書で明記し、
  過大な安全性主張を避けています（§5）。
- **A01 アクセス制御 / パストラバーサル**: `node_modules` 走査時の
  symlink 追跡禁止・走査範囲外パスの除外方針を §4 に明記しました。
- **機微情報の非混入**: 本書・fixture 仕様に実クレデンシャル・実在
  パッケージの脆弱性詳細は含めていません。

## 7. リスクと安全側の判断（担当「共同」タスクとしての明記）

本タスクは担当区分「共同」であり、本来は人間の方針決定を伴います。
自動運転モードでの実装のため、以下の判断ポイントはすべて**拒否側
（安全側）に倒して確定**しました。人間レビュー（PR）で妥当性を確認して
ください。

1. **Rule 1 の `scripts` フィールド違反扱い**（§3.1）: ライフサイクル
   スクリプトの存在自体を違反とする判断。過検知の可能性あり。
2. **`.d.ts` / `.map` / `.scss` / `.less` の拒否**（§3.2）: 実行コードでは
   ないが、用途がない・実行コードへの接続を示唆するという理由で拒否。
3. **allowlist 方式の採用**（§3 冒頭）: denylist より保守コストが高いが、
   未知の実行形式を構造的に防げる安全側の設計。

緩和方向（許可の追加）は例外機構（§3.3）または後続 PR で対応可能ですが、
逆方向（拒否の追加）は既存の取り込み済みパッケージに対して破壊的になり
うるため、初期設計は厳格側を正としています。
